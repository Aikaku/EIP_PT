# GoF 디자인 패턴 전체 정리

> Gang of Four — 23개 패턴, 생성(5) / 구조(7) / 행위(11)

---

## 분류 한눈에 보기

| 분류 | 패턴 이름 |
|------|---------|
| **생성** | Singleton, Factory Method, Abstract Factory, Builder, Prototype |
| **구조** | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy |
| **행위** | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor |

---

## 1. 생성 패턴 (Creational) — 5개

> 객체 **생성** 방식을 캡슐화

---

### 1-1. Singleton (싱글톤)

- **핵심**: 클래스 인스턴스를 **전역에서 단 하나**만 생성·공유
- **키워드**: 인스턴스 1개, private 생성자, 전역 접근점
- **사용 예**: DBCP(데이터베이스 커넥션 풀), 로그 매니저, 설정 객체

```java
class Singleton {
    private static Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) instance = new Singleton();
        return instance;
    }
}
```

> **기출 포인트**: `getInstance()` 메서드로 반환 / DBCP 연관 / private 생성자

---

### 1-2. Factory Method (팩토리 메서드)

- **핵심**: 객체 생성 인터페이스는 상위 클래스에 정의, **구체 클래스 결정은 서브클래스**에 위임
- **키워드**: 객체 생성을 서브클래스에, 인터페이스만 정의
- **구조**: Creator(추상) ← ConcreteCreator / Product(추상) ← ConcreteProduct

```
Creator.create() → abstract
    ↓ 서브클래스가 구현
ConcreteCreator.create() → new ConcreteProduct()
```

> **기출 포인트**: "생성을 **서브클래스**에 위임" = Factory Method

---

### 1-3. Abstract Factory (추상 팩토리)

- **핵심**: **관련 객체들의 집합(제품군)**을 그룹으로 생성하는 인터페이스 제공
- **키워드**: 연관된 서브클래스를 묶어 한 번에 교체, 제품군
- **Factory Method와 차이**: Factory Method = 한 종류 객체 / Abstract Factory = **관련 객체 여러 종류** 한 번에

```
AbstractFactory
├── createButton()
└── createCheckbox()
    ↓ (구현체 교체로 Windows↔Mac 전체 전환)
WindowsFactory / MacFactory
```

> **기출 포인트**: "연관된 서브클래스를 **묶어** 한 번에 교체"

---

### 1-4. Builder (빌더)

- **핵심**: 복잡한 객체 **생성 과정과 표현 방법을 분리** → 동일 생성 과정으로 다양한 결과
- **키워드**: 단계별 생성, 동일 과정 → 다른 결과
- **구조**: Director → Builder(추상) ← ConcreteBuilder → Product

```
Director.construct() {
    builder.buildPart1();
    builder.buildPart2();
    builder.buildPart3();
}
```

> **기출 포인트**: "생성 과정과 **표현 방법 분리**", "단계별 구성"

---

### 1-5. Prototype (프로토타입)

- **핵심**: 기존 객체를 **복제(clone)**해서 새 객체 생성
- **키워드**: clone(), 복제, 생성 비용이 클 때
- **사용 예**: 객체 초기화 비용이 비쌀 때(DB 조회 등), Java의 `Cloneable`

```java
class Product implements Cloneable {
    public Product clone() { return (Product) super.clone(); }
}
```

> **기출 포인트**: "**원본 객체를 복제**하여 생성", `clone()` 메서드

---

## 2. 구조 패턴 (Structural) — 7개

> 클래스나 객체를 **조합**하여 더 큰 구조 형성

---

### 2-1. Adapter (어댑터)

- **핵심**: 호환되지 않는 인터페이스를 **변환**하여 연결
- **키워드**: 인터페이스 변환, 호환성, 래퍼(Wrapper)
- **사용 예**: 110V↔220V 어댑터, 레거시 코드 재활용

```
Client → Target 인터페이스 → Adapter → Adaptee(기존 클래스)
```

> **기출 포인트**: "인터페이스가 **맞지 않는** 클래스를 사용할 수 있도록 **변환**"

---

### 2-2. Bridge (브리지)

- **핵심**: **추상부(기능)**와 **구현부**를 분리하여 각각 독립적으로 확장
- **키워드**: 추상부 ↔ 구현부 분리, 독립 확장

```
Shape(추상) ─────── DrawingAPI(구현 인터페이스)
├── Circle              ├── DrawingAPI1
└── Square              └── DrawingAPI2
```

> **기출 포인트**: "**구현부와 추상층을 분리**하여 독립적으로 확장"

---

### 2-3. Composite (컴포지트)

- **핵심**: 단일 객체와 복합 객체를 **동일한 인터페이스**로 처리 (트리 구조)
- **키워드**: 트리 구조, 단일·복합 동일 취급, 재귀 구조

```
Component (공통 인터페이스)
├── Leaf (단일 객체)
└── Composite (복합 객체 — 자식 목록 포함)
         └── [Component, Component, ...]
```

> **기출 포인트**: "**트리 구조**로 구성, 단일·복합 객체를 **구분 없이** 다룸"

---

### 2-4. Decorator (데코레이터)

- **핵심**: 객체에 **동적으로 기능을 추가**. 서브클래스 없이 기능 확장
- **키워드**: 동적 기능 추가, 감싸기(Wrapper), 런타임 확장

```
Component(인터페이스)
├── ConcreteComponent (원본)
└── Decorator(래퍼)
         └── ConcreteDecorator → ConcreteComponent 감싸서 기능 추가
```

> **기출 포인트**: "객체 간 **결합**을 통해 기능을 **동적으로 추가**"  
> ※ Proxy와 구별: Decorator=기능 추가, Proxy=접근 제어

---

### 2-5. Facade (퍼사드)

- **핵심**: 복잡한 서브시스템을 **단순한 통합 인터페이스**로 제공
- **키워드**: 단일 창구, 복잡성 은닉, 서브시스템 단순화

```
Client → Facade → SubsystemA
                → SubsystemB
                → SubsystemC
```

> **기출 포인트**: "복잡한 서브시스템을 **하나의 인터페이스**로 제공"

---

### 2-6. Flyweight (플라이웨이트)

- **핵심**: 동일하거나 유사한 객체를 **공유**하여 메모리 절약
- **키워드**: 인스턴스 공유, 메모리 절약, 다수의 유사 객체

```
FlyweightFactory(공유 풀) → 이미 있으면 기존 반환, 없으면 생성
```

- **내적 상태** (공유 가능): 변하지 않는 데이터
- **외적 상태** (공유 불가): 매번 달라지는 데이터

> **기출 포인트**: "인스턴스를 **공유**하여 **메모리 절약**"

---

### 2-7. Proxy (프록시)

- **핵심**: 실제 객체 앞에 **대리인(Proxy)**을 두어 접근 제어
- **키워드**: 대리인, 접근 제어, 지연 초기화, 보안

```
Client → Proxy → RealSubject
           ↑ 접근 제어 / 캐싱 / 인증 / 지연 로딩
```

| 종류 | 설명 |
|------|------|
| 가상 프록시 | 생성 비용 큰 객체의 지연 초기화 |
| 보호 프록시 | 접근 권한 제어 |
| 원격 프록시 | 네트워크 너머 객체 대리 |

> **기출 포인트**: "객체를 **대리**하여 **접근 제어**"  
> ※ Decorator와 구별: Proxy=접근제어, Decorator=기능추가

---

## 3. 행위 패턴 (Behavioral) — 11개

> 객체나 클래스 사이의 **알고리즘·책임 분배**

---

### 3-1. Chain of Responsibility (책임 연쇄)

- **핵심**: 요청을 처리할 수 있는 객체를 **연결 고리**로 만들어 순차 전달
- **키워드**: 처리 못 하면 다음으로 넘김, 느슨한 결합, 사슬

```
Client → Handler1 → Handler2 → Handler3 → null
              처리 못하면 다음으로 전달
```

> **기출 포인트**: "처리 못하면 **다음 객체로 책임 전달**"

---

### 3-2. Command (커맨드)

- **핵심**: 요청을 **객체 형태로 캡슐화** → 저장, 취소(Undo), 재실행 가능
- **키워드**: 요청 캡슐화, 실행 취소(Undo/Redo), 매크로

```
Client → Invoker.execute() → Command.execute() → Receiver.action()
                                  ↑ 요청이 객체화됨 → 저장/취소 가능
```

> **기출 포인트**: "요청을 **객체 형태로 캡슐화**, **취소·재실행** 가능"

---

### 3-3. Interpreter (인터프리터)

- **핵심**: 특정 **언어의 문법을 클래스로 표현**하여 해석
- **키워드**: 문법 표현, SQL, 통신 프로토콜, 정규식
- **구조**: 각 문법 규칙을 클래스로 정의 → 문장 트리 구조로 해석

> **기출 포인트**: "**언어의 문법을 표현**", SQL·정규식 개발 시 사용

---

### 3-4. Iterator (반복자 / 이터레이터)

- **핵심**: 컬렉션 내부 구조를 노출하지 않고 **순차 접근** 인터페이스 제공
- **키워드**: 순차 접근, 내부 구조 은닉, hasNext()/next()

```java
Iterator it = collection.iterator();
while (it.hasNext()) {
    Object item = it.next();
}
```

> **기출 포인트**: "**자료구조를 순차 접근**, 내부 구조 노출 없음"

---

### 3-5. Mediator (중재자)

- **핵심**: 객체 간 복잡한 상호작용을 **중재자 객체가 담당** → 의존성 감소
- **키워드**: 객체 간 통신 중앙화, N:N → N:1, 결합 감소

```
ObjectA ─┐
ObjectB ─┤→ Mediator ← ObjectC ─┤
ObjectD ─┘               ObjectE ─┘
```

> **기출 포인트**: "복잡한 **상호작용을 하나의 객체로 캡슐화**", 의존성 감소

---

### 3-6. Memento (메멘토)

- **핵심**: 객체의 내부 상태를 **스냅샷**으로 저장 → 이전 상태로 복원
- **키워드**: 상태 저장·복원, Undo, 스냅샷

```
Originator → Memento(상태 저장) → Caretaker(보관)
                     ↑ 복원 시 Originator에게 반환
```

> **기출 포인트**: "**상태를 저장**했다가 **이전 상태로 복원**(Undo)"

---

### 3-7. Observer (옵서버)

- **핵심**: 한 객체 상태 변화 시 **의존 객체들에게 자동 알림** (일대다 의존)
- **키워드**: 발행-구독(Pub-Sub), 이벤트 리스너, 일대다

```
Subject(Observable)
├── attach(Observer)
├── detach(Observer)
└── notify() → 모든 Observer.update() 호출
```

> **기출 포인트**: "상태 변화 시 **자동으로 알림**, **일대다** 의존"

---

### 3-8. State (상태)

- **핵심**: 객체의 **상태에 따라 동일 메서드가 다른 동작** 수행 (상태를 클래스로)
- **키워드**: 상태 캡슐화, 조건문 대체, 상태 객체 교체

```
Context ─→ State(인터페이스)
              ├── StateA.handle()
              └── StateB.handle()
```

> **기출 포인트**: "**상태에 따라 동일 동작이 다르게** 처리", 상태 캡슐화

---

### 3-9. Strategy (전략)

- **핵심**: 동일 목적의 알고리즘을 **클래스로 각각 캡슐화** → 상호 교환 가능
- **키워드**: 알고리즘 교체, 런타임 전략 변경, 캡슐화

```
Context ─→ Strategy(인터페이스)
              ├── ConcreteStrategyA.execute()
              └── ConcreteStrategyB.execute()
```

> **기출 포인트**: "알고리즘을 **캡슐화**하여 **상호 교환** 가능"  
> ※ State와 구별: Strategy=알고리즘 교체, State=상태에 따른 동작 변화

---

### 3-10. Template Method (템플릿 메서드)

- **핵심**: **상위 클래스에서 알고리즘 골격** 정의, **세부 구현은 서브클래스**에서
- **키워드**: 알고리즘 골격, Hook 메서드, 코드 재사용

```java
abstract class Game {
    final void play() {   // 골격 고정
        initialize();
        start();          // 추상 메서드 → 서브클래스 구현
        end();
    }
    abstract void start();
    abstract void end();
    void initialize() { /* 공통 구현 */ }
}
```

> **기출 포인트**: "**골격은 상위**, **세부 구현은 하위** 클래스"

---

### 3-11. Visitor (방문자)

- **핵심**: 데이터 구조(Element)는 변경 없이 **새로운 연산(Visitor)을 분리**
- **키워드**: 구조-기능 분리, 데이터 구조 변경 없이 새 연산 추가

```
Element.accept(Visitor)
    → Visitor.visit(ConcreteElement)
         ↑ 새로운 기능은 Visitor에만 추가
```

> **기출 포인트**: "데이터 구조와 **처리 기능을 분리**", "구조 변경 없이 연산 추가"

---

## 빠른 암기표 — 혼동 패턴 비교

### 생성 패턴 비교

| 패턴 | 핵심 한 줄 | 키워드 |
|------|---------|-------|
| Singleton | 인스턴스 **1개만** | private 생성자, getInstance() |
| Factory Method | 생성을 **서브클래스**에 위임 | 인터페이스만 정의 |
| Abstract Factory | **제품군** 통째로 생성 | 연관 객체 묶어 교체 |
| Builder | **단계별** 생성, 과정·표현 분리 | Director, 복잡한 객체 |
| Prototype | **복제(clone)**으로 생성 | 생성 비용 클 때 |

### 구조 패턴 비교

| 패턴 | 핵심 한 줄 | 키워드 |
|------|---------|-------|
| Adapter | 인터페이스 **변환** | 호환성, Wrapper |
| Bridge | **추상↔구현 분리** | 독립 확장 |
| Composite | **트리 구조**, 단일·복합 동일 취급 | 재귀, 파일시스템 |
| Decorator | 동적 **기능 추가** | Wrapper, 런타임 확장 |
| Facade | 복잡한 시스템을 **단순 인터페이스** | 단일 창구 |
| Flyweight | 공유로 **메모리 절약** | 인스턴스 공유 |
| Proxy | **대리인**, 접근 제어 | 지연 초기화, 보안 |

### 행위 패턴 비교

| 패턴 | 핵심 한 줄 | 키워드 |
|------|---------|-------|
| Chain of Responsibility | 처리 못 하면 **다음으로 전달** | 사슬, 느슨한 결합 |
| Command | 요청을 **객체로 캡슐화** | Undo/Redo, 매크로 |
| Interpreter | **문법 표현** 클래스화 | SQL, 정규식 |
| Iterator | 컬렉션 **순차 접근** | 내부 구조 은닉 |
| Mediator | 상호작용을 **중재자가 담당** | N:N → N:1 |
| Memento | **상태 저장·복원** | Undo, 스냅샷 |
| Observer | 상태 변화 → **자동 알림** | Pub-Sub, 일대다 |
| State | **상태**에 따라 동작 다름 | 조건문 대체 |
| Strategy | **알고리즘** 교체 가능 | 캡슐화, 교환 |
| Template Method | **골격 상위**, 세부 하위 | Hook, 재사용 |
| Visitor | **구조·기능 분리** | 연산 추가 용이 |

## 단답형 퀴즈 — 무작위 순서 (실전용)

> 아래 설명을 읽고 해당하는 GoF 디자인 패턴 이름을 작성하시오.

---

**Q01.** 한 객체의 상태가 변화하면 그 객체에 의존하는 모든 객체에게 자동으로 알림이 전달된다. 일대다(1:N) 의존 관계를 가지며, 주로 이벤트 처리나 발행-구독(Pub-Sub) 구조에 활용된다.

**Q02.** 실제 객체에 대한 접근을 제어하기 위해 대리인(Surrogate) 객체를 앞에 둔다. 지연 초기화, 접근 권한 제어, 원격 객체 대리 등에 활용된다.

**Q03.** 복잡한 객체를 생성하는 과정과 표현 방법을 분리한다. 동일한 생성 과정을 거쳐 서로 다른 결과물을 만들 수 있으며, Director와 ConcreteBuilder로 구성된다.

**Q04.** 요청을 처리할 객체들을 사슬(Chain)로 연결한다. 각 객체는 요청을 처리할 수 없으면 다음 객체로 전달하며, 처리 객체와 요청자 간 결합도를 줄인다.

**Q05.** 기존 객체에 서브클래스 없이 새로운 기능을 동적으로 덧붙인다. 래퍼(Wrapper) 형태로 감싸며, 런타임에 기능을 확장할 수 있다.

**Q06.** 클래스의 인스턴스가 오직 하나임을 보장하고 전역에서 접근할 수 있는 단일 접근점을 제공한다. 데이터베이스 커넥션 풀(DBCP)이나 로그 매니저에 활용된다.

**Q07.** 데이터 구조(Element)와 처리 기능(연산)을 분리한다. 데이터 구조는 변경하지 않고 새로운 연산을 Visitor 객체로 추가할 수 있다.

**Q08.** 객체 생성을 위한 인터페이스는 상위 클래스에서 정의하되, 어떤 클래스의 인스턴스를 생성할지는 서브클래스가 결정한다.

**Q09.** 같거나 유사한 객체 다수를 생성할 때 공유(Sharing)를 통해 메모리 사용량을 최소화한다. 내적 상태는 공유하고 외적 상태는 외부에서 관리한다.

**Q10.** 객체의 내부 상태를 외부에 노출하지 않고 스냅샷 형태로 저장한다. 저장된 상태는 나중에 복원(Undo)하는 데 사용된다.

**Q11.** 호환되지 않는 두 인터페이스 사이를 연결해 주는 변환기 역할을 한다. 기존 클래스를 수정하지 않고 새로운 인터페이스에 맞게 재활용할 수 있다.

**Q12.** 알고리즘의 집합을 정의하고 각각을 캡슐화한다. 알고리즘들은 상호 교환 가능하며 클라이언트와 독립적으로 변경할 수 있다.

**Q13.** 객체들을 트리 구조로 구성하여 부분-전체 계층을 표현한다. 클라이언트는 단일 객체와 복합 객체를 동일한 인터페이스로 다룬다.

**Q14.** 알고리즘의 골격(skeleton)을 상위 클래스에서 정의하고, 세부 구현은 서브클래스에서 담당한다. 공통 코드는 상위 클래스에 두어 코드 중복을 줄인다.

**Q15.** 기존 객체를 원형(Prototype)으로 삼아 복제(clone)하여 새로운 객체를 생성한다. 객체 생성 비용이 클 때 유용하다.

**Q16.** 집합체(Collection) 내부 표현을 노출하지 않고 모든 항목에 순차적으로 접근하는 방법을 제공한다. `hasNext()`, `next()` 메서드가 특징이다.

**Q17.** 기능을 처리하는 추상 클래스와 구현을 담당하는 추상 클래스를 분리한다. 추상부와 구현부가 각각 독립적으로 확장될 수 있다.

**Q18.** 요청을 객체 형태로 캡슐화하여 저장하거나 로그로 기록하고, 작업 취소(Undo) 및 재실행(Redo)이 가능하도록 한다.

**Q19.** 여러 서브시스템의 복잡한 인터페이스를 클라이언트에게 단순한 단일 인터페이스로 제공한다. 클라이언트는 서브시스템 내부 구조를 알 필요 없다.

**Q20.** 객체 간 복잡한 N:N 상호작용을 하나의 중재자 객체를 통해 N:1로 단순화한다. 객체 간 직접 참조를 없애 결합도를 낮춘다.

**Q21.** 서로 관련된 여러 종류의 객체를 일관된 방식으로 생성하는 인터페이스를 제공한다. 구체 클래스를 지정하지 않고 관련 객체들의 집합(제품군)을 한꺼번에 교체할 수 있다.

**Q22.** 객체 내부 상태를 별도 클래스로 캡슐화한다. 상태가 바뀌면 동일한 메서드 호출에도 서로 다른 동작이 수행되며, 복잡한 조건문을 대체한다.

**Q23.** 언어의 문법을 클래스 계층으로 표현하고 그 언어로 작성된 문장을 해석하는 해석기를 구현한다. SQL, 정규 표현식 처리 등에 활용된다.
