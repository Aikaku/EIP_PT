**Q01.**
> 소프트웨어 개발 모형 중, 위험 최소화에 초점을 맞춘 모형으로, **계획 수립 → 위험 분석 → 개발 및 검증 → 고객 평가**의 4단계를 반복하며 진행되는 모형은?

**정답**: 나선형(Spiral) 모형

**해설**:
- 보헴(Boehm)이 1988년 제안한 모형
- 폭포수 모형 + 프로토타입 모형의 장점을 결합하여 위험 분석을 추가
- 4단계를 나선 모양으로 반복: ① 계획 수립 → ② 위험 분석 → ③ 개발 및 검증 → ④ 고객 평가
- **위험 최소화**가 핵심 — 각 사이클마다 위험 분석 단계를 거침
- 대규모·복잡한 시스템에 적합; 비용이 많이 드는 단점
- 혼동 주의: 폭포수(단계별 순차, 피드백 없음) / 프로토타입(시제품 먼저) / 나선형(위험 분석 반복) / 애자일(짧은 이터레이션, 사람 중심)

**Q02.**
> XP(eXtreme Programming)의 주요 실천 방법 중, 테스트 케이스를 먼저 작성한 후 이를 통과하는 코드를 작성하는 개발 방법은?

**정답**: 테스트 주도 개발(TDD, Test Driven Development)

**해설**:
- XP(eXtreme Programming): 켄트 벡(Kent Beck)이 제안한 애자일 방법론
- TDD 절차: ① 실패하는 테스트 케이스 작성 → ② 테스트 통과하는 코드 작성 → ③ 코드 리팩토링
- 핵심: **테스트 먼저, 코드 나중**
- XP의 다른 실천 방법들: 짝 프로그래밍(Pair Programming), 지속적 통합(CI), 소규모 릴리즈, 코드 공유 등

**Q03.**
> COCOMO 소프트웨어 개발 유형 중, 기관 내부에서 개발된 중소 규모의 소프트웨어로 일괄 자료 처리나 과학기술 계산용으로 **5만 라인 이하**인 유형은?

**정답**: 조직형(Organic)

**해설**:
- COCOMO(COnstructive COst MOdel): 보헴이 제안한 비용 산정 모형
- 3가지 유형 비교:

| 유형 | 규모 | 특징 |
|------|------|------|
| **조직형(Organic)** | 5만 라인 이하 | 기관 내부, 소규모, 친숙한 환경 |
| **반분리형(Semi-detached)** | 30만 라인 이하 | 중간 규모, 혼합 경험 |
| **내장형(Embedded)** | 30만 라인 초과 | 하드웨어·실시간, 제약 많음 |

**Q04.**
> 소프트웨어 비용 산정 기법 중, Rayleigh-Norden 곡선을 이용하여 소프트웨어 수명 주기의 전 과정 동안에 사용될 인력의 분포를 가정하는 기법은?

**정답**: Putnam 모형

**해설**:
- Putnam이 제안한 수학적 비용 산정 모형
- **Rayleigh-Norden 곡선** 사용: 시간에 따른 인력 투입 곡선
- 대형 프로젝트의 노력(인력)과 기간 사이의 관계를 수식으로 표현
- SLIM(Software Lifecycle Management) 자동화 도구를 이용해 계산
- 혼동 주의: COCOMO(규모별 공식) / Putnam(곡선 기반 수명 전체) / 기능 점수(FP, 입출력/파일/인터페이스 수 기반)

**Q05.**
> CMM을 기반으로 만들어진 소프트웨어 개발 능력 성숙도 모형으로, **5단계(초기 → 관리 → 정의 → 정량적 관리 → 최적화)**로 구성되는 모형은?

**정답**: CMMI(Capability Maturity Model Integration)

**해설**:
- CMM(카네기멜론 대학 SEI)을 통합·발전시킨 프로세스 개선 모델
- 5단계 성숙도:

| 단계 | 이름 | 특징 |
|------|------|------|
| 1 | 초기(Initial) | 프로세스 없음, 혼란 |
| 2 | 관리(Managed) | 기본 프로젝트 관리 |
| 3 | 정의(Defined) | 조직 표준 프로세스 정립 |
| 4 | 정량적 관리(Quantitatively Managed) | 통계적 품질 관리 |
| 5 | 최적화(Optimizing) | 지속적 개선, 최고 수준 |

**Q06.**
> 소프트웨어 프로세스 개선 및 능력 측정을 위한 국제 표준으로, **ISO/IEC 15504**라고도 하며 소프트웨어 프로세스의 평가와 개선을 지원하는 것은?

**정답**: SPICE(ISO/IEC 15504)

**해설**:
- SPICE = Software Process Improvement and Capability dEtermination
- 공식 국제 표준 번호: **ISO/IEC 15504**
- 목적: 소프트웨어 프로세스를 **평가**하고 **개선** 방향 제시
- 5개 프로세스 범주: 고객-공급자 / 공학 / 지원 / 관리 / 조직 프로세스
- CMMI와 목적은 유사하지만 국제 표준(ISO)이라는 점이 차이

**Q07.**
> 데이터베이스의 스키마 3단계 중, 사용자나 응용 프로그래머가 각 개인의 입장에서 필요로 하는 데이터베이스의 논리적 구조를 정의한 것은?

**정답**: 외부 스키마(External Schema)

**해설**:
- 스키마 3단계: **외부 → 개념 → 내부**
- 외부 스키마: 개별 사용자/응용 프로그램 관점의 뷰(View)
  - "서브 스키마(Sub Schema)"라고도 함
  - **여러 개** 존재 가능(사용자마다 다른 뷰)
- 개념 스키마: 조직 전체 관점, 중간 단계, **1개** 존재
- 내부 스키마: 물리적 저장 관점, **1개** 존재

**Q08.**
> 데이터베이스의 스키마 3단계 중, 물리적 저장 장치 입장에서 본 데이터베이스 구조로, 실제로 데이터베이스에 저장될 레코드의 형식, 저장 데이터 항목의 표현 방법 등을 정의한 것은?

**정답**: 내부 스키마(Internal Schema)

**해설**:
- 내부 스키마: 물리적 저장 장치(디스크) 관점의 가장 낮은 단계
- 실제 저장 형식, 인덱스, 접근 경로, 압축 방법 등을 정의
- **1개**만 존재(조직에 하나의 물리 DB)
- DBA가 관리하는 영역

**Q10.**
> 릴레이션의 구성 요소 중, 릴레이션에 포함된 **튜플의 수**를 의미하는 것은?

**정답**: 카디널리티(Cardinality, 기수)

**해설**:
- 릴레이션 용어 정리:

| 용어 | 의미 | 비유 |
|------|------|------|
| **카디널리티(Cardinality)** | 튜플(행)의 수 | 행 수 |
| **디그리(Degree, 차수)** | 속성(열)의 수 | 컬럼 수 |
| 튜플(Tuple) | 하나의 행(레코드) | 한 명의 데이터 |
| 속성(Attribute) | 하나의 열(필드) | 이름, 나이 등 |

- 카디널리티가 높다 = 데이터(행)가 많다 → 선택도 낮아짐

**Q11.**

**정답**: 디그리(Degree, 차수)

**해설**:
- 디그리 = 속성(Attribute, 열)의 수
- 예: 학생(학번, 이름, 학과) → 디그리 = 3

**Q12.**
> 키의 종류 중, **유일성과 최소성**을 모두 만족하는 키는?

**정답**: 후보키(Candidate Key)

**해설**:
- **유일성**: 모든 튜플을 유일하게 식별할 수 있음
- **최소성**: 꼭 필요한 최소한의 속성으로만 구성됨(속성을 하나라도 빼면 유일성 깨짐)
- 키의 포함 관계: 기본키 ⊆ 후보키 ⊆ 슈퍼키

| 키 종류 | 유일성 | 최소성 |
|---------|--------|--------|
| 슈퍼키 | ✓ | ✗ |
| **후보키** | ✓ | ✓ |
| 기본키 | ✓ | ✓ (후보키 중 선택) |
| 외래키 | ✗ | - |

**Q13.**
> 키의 종류 중, 후보키가 두 개 이상일 때 그 중에서 기본키로 선택되지 못하고 남은 키는?

**정답**: 대체키(Alternate Key)

**해설**:
- 후보키가 여러 개일 때 → 하나를 기본키로 선택 → 나머지가 대체키
- 예: 학생 테이블에 (학번), (주민번호) 둘 다 후보키
  - 학번을 기본키로 선택 → 주민번호가 대체키
- 대체키도 유일성·최소성을 만족하는 후보키임

**Q14.**
> 데이터베이스 무결성 중, 릴레이션에서 기본키를 구성하는 속성 값이 **NULL이거나 중복 값을 가질 수 없다**는 제약 조건은?

**정답**: 개체 무결성(Entity Integrity)

**해설**:
- 무결성 종류 비교:

| 무결성 | 내용 |
|--------|------|
| **개체 무결성** | 기본키는 NULL 불가, 중복 불가 |
| **참조 무결성** | 외래키 값은 참조 테이블의 기본키 값이거나 NULL |
| **도메인 무결성** | 속성 값은 정의된 도메인(범위) 내여야 함 |

- 핵심 키워드: 기본키 → NULL 불가, 중복 불가 → 개체 무결성

**Q15.**
> 관계대수 연산자 중, 릴레이션에서 **조건을 만족하는 튜플(행)**을 추출하는 연산으로 σ로 표현되는 것은?

**Q17.**
> 데이터베이스 이상(Anomaly) 중, 테이블에서 **한 튜플을 삭제할 때** 불필요하게 다른 정보까지 함께 삭제되는 현상은?

**정답**: 삭제 이상(Deletion Anomaly)

**해설**:
- 이상(Anomaly) 3가지 — 정규화가 필요한 이유:

| 이상 종류 | 발생 상황 | 예시 |
|-----------|-----------|------|
| **삽입 이상** | 데이터 삽입 시 불필요한 데이터도 삽입해야 함 | 수강 안 한 학생 등록 불가 |
| **삭제 이상** | 하나 삭제 시 다른 정보까지 삭제됨 | 학생 정보 삭제 시 강의 정보도 사라짐 |
| **갱신 이상** | 중복 저장된 데이터 일부만 변경 시 불일치 발생 | 교수 이름 수정 시 일부만 반영 |

**Q18.**
> 테이블의 속성 X의 값을 알면 항상 Y의 값을 하나만 결정할 수 있을 때, "Y는 X에 ( )한다" 또는 "X가 Y를 ( )한다"고 한다. 이때의 관계는?

**정답**: 함수적 종속(Functional Dependency)

**해설**:
- X → Y: "X가 Y를 **함수적으로 결정**한다" 또는 "Y는 X에 **함수적으로 종속**된다"
- 예: 학번 → 이름 (학번을 알면 이름이 하나로 결정됨)
- 정규화의 기반이 되는 핵심 개념
- 종류: 완전 함수적 종속(기본키 전체에 종속), 부분 함수적 종속(기본키 일부에 종속), 이행적 종속(X→Y, Y→Z일 때 X→Z)

---

**Q19.**
> 함수적 종속 중, X → Y이고 Y → Z일 때 X → Z를 만족하는 관계를 무엇이라 하는가?

**정답**: 이행적 함수적 종속(Transitive Functional Dependency)

**해설**:
- X → Y → Z 이면 X → Z 성립
- 예: 학번 → 학과 → 학과장 이면 학번 → 학과장도 성립
- **3NF에서 제거**해야 하는 종속 관계
- 이행적 종속이 존재하면 갱신 이상 발생 가능

**Q20.**
> 정규화 단계 중, 테이블의 **모든 속성 값이 원자 값(Atomic Value)**만으로 되어 있는 정규형은?

**정답**: 제1정규형(1NF)

**해설**:
- 원자값 = 더 이상 분해할 수 없는 단일 값
- 1NF 위반 예: 취미 속성에 "독서, 운동" 처럼 복수 값이 있는 경우
- 정규화 단계 순서: **비정규 → 1NF → 2NF → 3NF → BCNF → 4NF → 5NF**
- 각 단계는 이전 단계를 만족해야 하는 누적 구조

**Q21.**
> 정규화 단계 중, 1NF를 만족하면서 기본키가 아닌 모든 속성이 기본키에 대해 **완전 함수적 종속**을 만족하는 정규형은?

**정답**: 제2정규형(2NF)

**해설**:
- 완전 함수적 종속: 기본키 **전체**에 종속 (기본키의 일부에만 종속되면 위반)
- **부분 함수적 종속** 제거 → 2NF
- 2NF 위반 예: 기본키가 (학번, 과목코드)인데, 이름이 학번에만 종속
  - 이름은 기본키 전체가 아닌 일부에만 종속 → 부분 종속 → 2NF 위반
- 해결: 부분 종속 속성을 별도 테이블로 분리

---

**Q22.**
> 정규화 단계 중, 2NF를 만족하면서 기본키가 아닌 모든 속성이 기본키에 대해 **이행적 함수적 종속을 만족하지 않는** 정규형은?

**정답**: 제3정규형(3NF)

**해설**:
- **이행적 함수적 종속 제거** → 3NF
- 3NF 위반 예: 학번→학과, 학과→학과장 이면 학번→학과장(이행적 종속)
  - 학과장이 기본키(학번)에 직접 종속이 아닌 학과를 통해 간접 종속
- 해결: 이행 종속 속성을 별도 테이블로 분리
- BCNF와 차이: 3NF는 결정자가 후보키가 아니어도 허용, BCNF는 모든 결정자가 후보키여야 함

**Q23.**
> 정규화된 데이터 모델을 의도적으로 **통합, 중복, 분리**하여 정규화 원칙을 위배하는 행위는?

**정답**: 반정규화(Denormalization)

**해설**:
- 정규화: 이상 현상 제거, 데이터 일관성 보장 → 테이블 분리됨 → 조회 시 JOIN 많아짐
- 반정규화: 조회 성능 향상을 위해 의도적으로 중복 허용 또는 테이블 통합
- 반정규화의 목적: **조회(SELECT) 성능 향상** (INSERT/UPDATE/DELETE 성능 저하 감수)
- 방법: 테이블 병합, 테이블 분할, 컬럼 중복 추가, 파생 컬럼 추가 등

**Q24.**

**해설**:

**Q25.**
> 트랜잭션의 특성(ACID) 중, 트랜잭션의 연산은 데이터베이스에 모두 반영(Commit)되거나 전혀 반영되지 않아야 한다(Rollback)는 특성은?

**정답**: 원자성(Atomicity)

**해설**:
- ACID 4가지 특성:

| 특성 | 영문 | 핵심 키워드 |
|------|------|------------|
| **원자성** | Atomicity | All or Nothing, Commit/Rollback |
| 일관성 | Consistency | 트랜잭션 전후 DB 일관성 유지 |
| 독립성 | Isolation | 다른 트랜잭션 간섭 불가 |
| 영속성 | Durability | Commit된 결과는 영구 저장 |

- 원자성: 은행 이체 예시 — 송금 계좌 출금과 수신 계좌 입금이 **둘 다 성공**하거나 **둘 다 취소**되어야 함

**Q26.**
> 트랜잭션의 특성(ACID) 중, 둘 이상의 트랜잭션이 동시에 병행 실행되는 경우 어느 하나의 트랜잭션 실행 중에 다른 트랜잭션의 연산이 끼어들 수 없다는 특성은?

**정답**: 독립성(Isolation) / 격리성

**해설**:
- 독립성(격리성): 병행 실행 시 다른 트랜잭션의 연산이 **끼어들 수 없음**
- 직렬화(Serializability)와 관련 — 마치 순차적으로 실행한 것과 동일한 결과
- 격리 수준(Isolation Level): Read Uncommitted → Read Committed → Repeatable Read → Serializable (높을수록 안전하지만 성능↓)
- 독립성 보장 기법: 잠금(Locking), 타임스탬프, MVCC 등

**Q27.**

**정답**: 뷰(View)

**해설**:
- 뷰: 하나 이상의 기본 테이블로부터 유도된 **가상 테이블**
- 실제 데이터는 저장되지 않고, 뷰 정의(쿼리)만 저장됨
- 뷰의 장점: 보안(민감 컬럼 숨김), 단순화(복잡한 쿼리 간소화), 독립성
- 뷰의 단점: 삽입·수정·삭제 제한 (일부 뷰는 DML 불가)
- `CREATE VIEW 뷰이름 AS SELECT ...` 로 생성

**Q28.**
> 비상사태 또는 업무 중단 시점으로부터 **복구 가능한 기준점**을 의미하는 것으로, 데이터를 어느 시점으로 복원할 수 있는지를 나타내는 것은? (영문 약어)

|------|------|------|

| **RTO** (목표 복구 시간) | 장애 발생 후 얼마나 빨리 복구하는가 | **얼마나 빨리** 복구하나? |

**Q34.**
> 정렬 알고리즘 중, n개의 레코드 중에서 최솟값을 찾아 첫 번째 레코드 위치에 놓고, 나머지 (n-1)개 중에서 다시 최솟값을 찾아 두 번째 레코드 위치에 놓는 방식을 반복하는 정렬은?

**정답**: 선택 정렬(Selection Sort)

**해설**:
- 매 패스마다 **최솟값을 선택**해서 앞으로 이동
- 시간 복잡도: 평균·최악 모두 **O(n²)**
- 교환 횟수가 적음 (최대 n-1번)
- 불안정(Unstable) 정렬

| 정렬 | 방법 | 시간 복잡도 |
|------|------|------------|
| 선택 | 최솟값 선택 후 교환 | O(n²) |
| 버블 | 인접 원소 비교·교환 | O(n²) |
| 삽입 | 적절한 위치에 삽입 | O(n²) |
| 퀵 | 피벗 기준 분할 | 평균 O(nlogn) |
| 병합 | 분할 후 병합 | O(nlogn) |

**Q35.**
> 정렬 알고리즘 중, 인접한 두 개의 레코드 값을 비교하여 그 크기에 따라 레코드 위치를 서로 교환하는 정렬로, 평균·최악 모두 O(n²)인 정렬은?

**정답**: 버블 정렬(Bubble Sort)

**해설**:
- 인접한 두 원소를 비교 → 크면 교환 → 반복
- 1패스마다 가장 큰 값이 맨 뒤로 이동 (거품이 올라오듯)
- 구현이 가장 단순
- 시간 복잡도: 평균·최악 O(n²), 최선 O(n) (이미 정렬된 경우)
- 안정(Stable) 정렬

**Q36.**

**Q43.**
> 객체지향 설계 원칙(SOLID) 중, **기존의 코드를 변경하지 않고 기능을 추가할 수 있도록** 설계해야 한다는 원칙은?

**정답**: 개방-폐쇄 원칙(OCP, Open-Closed Principle)

**해설**:
- 확장에는 **열려**(Open) 있고, 수정에는 **닫혀**(Closed) 있어야 함
- 새 기능 추가 시 기존 코드 수정 없이 확장(상속·인터페이스)으로 구현
- SOLID 5원칙 암기:

| 약어 | 이름 | 핵심 |
|------|------|------|
| **S** | SRP (단일 책임) | 클래스는 하나의 책임만 |
| **O** | OCP (개방-폐쇄) | 확장 Open, 수정 Closed |
| **L** | LSP (리스코프 치환) | 자식이 부모를 대체 가능 |
| **I** | ISP (인터페이스 분리) | 사용 안 하는 인터페이스 의존 금지 |
| **D** | DIP (의존 역전) | 추상화에 의존 |

---

**Q44.**
> 객체지향 설계 원칙(SOLID) 중, **자식 클래스는 최소한 부모 클래스의 기능은 수행할 수 있어야** 한다는 원칙은?

**정답**: 리스코프 치환 원칙(LSP, Liskov Substitution Principle)

**해설**:
- 바바라 리스코프(Barbara Liskov)가 제안
- 부모 클래스 자리에 자식 클래스를 사용해도 프로그램이 정상 동작해야 함
- 예: Bird 클래스에 fly() 메서드가 있을 때, Penguin(새)을 자식으로 만들면 LSP 위반 (펭귄은 날 수 없음)
- 상속 관계를 설계할 때 반드시 고려해야 하는 원칙

---

**Q45.**
> 모듈 간의 상호 의존하는 정도를 나타내는 척도로, **약할수록 품질이 높고** 강할수록 품질이 낮은 것은?

**정답**: 결합도(Coupling)

**해설**:
- 결합도: 모듈 간 **의존 정도** → **낮을수록** 좋음
- 결합도 강도 순서 (강 → 약, 암기 필수):
  - **내**용 > **공**통 > **외**부 > **제**어 > **스**탬프 > **자**료
  - 암기법: "**내공외제스자**"

| 결합도 | 특징 |
|--------|------|
| 내용 결합도 | 다른 모듈 내부 직접 참조·수정 (가장 강함) |
| 공통 결합도 | 전역 변수 공유 |
| 외부 결합도 | 외부 선언 변수 참조 |
| 제어 결합도 | 제어 신호(플래그) 전달 |
| 스탬프 결합도 | 자료 구조(배열·레코드) 전달 |
| 자료 결합도 | 단순 값만 전달 (가장 약함) |

---

**Q46.**
> 모듈의 내부 요소들이 서로 관련되어 있는 정도를 나타내는 척도로, **강할수록 품질이 높고** 약할수록 품질이 낮은 것은?

**정답**: 응집도(Cohesion)

**해설**:
- 응집도: 모듈 내 요소들의 **관련 정도** → **높을수록** 좋음
- 응집도 강도 순서 (강 → 약, 암기 필수):
  - **기**능 > **순**차 > **교**환 > **절**차 > **시**간 > **논**리 > **우**연
  - 암기법: "**기순교절시논우**"

| 응집도 | 특징 |
|--------|------|
| 기능적 | 단일 기능만 수행 (가장 강함) |
| 순차적 | 앞 출력 → 다음 입력 |
| 교환(통신)적 | 같은 입출력, 다른 기능 |
| 절차적 | 순서만 있음, 데이터 흐름 없음 |
| 시간적 | 특정 시간대 실행 묶음 |
| 논리적 | 유사 성격 기능 묶음 |
| 우연적 | 관련 없는 기능 집합 (가장 약함) |

---

**Q47.**
> 어떤 모듈을 제어하는 모듈의 수를 의미하는 것은?

**정답**: 팬인(Fan-In)

**해설**:
- 팬인 vs 팬아웃:

| 용어 | 의미 | 해석 |
|------|------|------|
| **팬인(Fan-In)** | 해당 모듈을 **호출하는** 모듈의 수 | 들어오는 화살표 수 |
| **팬아웃(Fan-Out)** | 해당 모듈이 **호출하는** 모듈의 수 | 나가는 화살표 수 |

- 팬인 높음 → 공유도 높음 → 중요도 높음 → 철저한 테스트 필요
- 팬아웃 높음 → 복잡도 높음 → 설계 개선 고려 필요
- 이상적: 팬인↑ 팬아웃↓

---

**Q48.**
> 어떤 모듈에 의해 제어되는 모듈의 수를 의미하는 것은?

**정답**: 팬아웃(Fan-Out)

**Q49.**
> 응집도의 종류 중, 모듈 내부의 각 구성 요소들이 서로 관련 없는 요소로만 구성된 경우로 **응집도가 가장 낮은** 것은?

**정답**: 우연적 응집도(Coincidental Cohesion)

**해설**:
- 우연적 응집도: 서로 관련 없는 기능들이 우연히 한 모듈에 묶인 경우
- 응집도 가장 낮음 → 품질 가장 나쁨
- 예: "기타 처리" 모듈에 로그 출력, 화면 초기화, 파일 삭제가 모두 포함

---

**Q50.**
> 응집도의 종류 중, 모듈 내부의 모든 기능 요소들이 단일 문제와 연관되어 수행되는 경우로 **응집도가 가장 높은** 것은?

**정답**: 기능적 응집도(Functional Cohesion)

**해설**:
- 기능적 응집도: 모듈 내 모든 요소가 **오직 하나의 기능**만을 수행
- 응집도 가장 높음 → 품질 가장 좋음
- 예: "학생 성적 계산" 모듈이 오직 성적 계산만 담당
- 단일 책임 원칙(SRP)과 연결되는 개념

---

**Q51.**
> 디자인 패턴을 생성 패턴, 구조 패턴, 행위 패턴으로 분류한 사람(단체)은?

**정답**: GOF(Gang of Four)

**해설**:
- GOF = Gang of Four: 에리히 감마(Gamma), 리처드 헬름(Helm), 랄프 존슨(Johnson), 존 블리시데스(Vlissides) 4명
- 1994년 《Design Patterns》 출판, 23가지 디자인 패턴 정리·분류
- 패턴 3가지 분류:

| 분류 | 패턴 수 | 목적 |
|------|---------|------|
| **생성 패턴** | 5개 | 객체 **생성** 방식 (Singleton, Factory Method, Abstract Factory, Builder, Prototype) |
| **구조 패턴** | 7개 | 클래스·객체 **조합** 구조 (Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy) |
| **행위 패턴** | 11개 | 객체 간 **상호작용·책임** (Command, Iterator, Observer, Strategy, Template Method 등) |

---

**Q52.**
> 디자인 패턴 중, 클래스 내에서 인스턴스가 하나뿐임을 보장하며, 불필요한 메모리 낭비를 최소화하는 **생성 패턴**은?

**정답**: 싱글톤(Singleton)

**해설**:
- **생성 패턴** — 인스턴스가 **단 하나**만 존재하도록 보장
- 전역 접근점 제공 (static 메서드로 인스턴스 반환)
- 사용 예: DB 연결 객체, 설정(Configuration) 관리, 로그 매니저
- 구현 방법: private 생성자 + static 인스턴스 변수 + static getInstance() 메서드

---

**Q53.**
> 디자인 패턴 중, 호환성이 없는 클래스들의 인터페이스를 다른 클래스가 이용할 수 있도록 변환해 주는 **구조 패턴**은?

**정답**: 어댑터(Adapter)

**해설**:
- **구조 패턴** — 호환되지 않는 인터페이스를 연결하는 변환기 역할
- 실생활 비유: 220V → 110V 전압 변환 어댑터
- 기존 코드를 수정하지 않고 새로운 인터페이스와 연결 가능
- 래퍼(Wrapper) 패턴이라고도 함

---

**Q54.**
> 디자인 패턴 중, 요청을 객체의 형태로 캡슐화하여 재이용하거나 취소할 수 있도록 요청에 필요한 정보를 저장하거나 로그에 남기는 **행위 패턴**은?

**정답**: 커맨드(Command)

**해설**:
- **행위 패턴** — 요청(명령)을 객체로 캡슐화
- 특징: 실행 취소(Undo), 재실행(Redo) 구현 가능, 요청을 큐에 저장 가능
- 예: 텍스트 편집기의 Ctrl+Z(Undo) 기능
- 구성: Command(인터페이스), ConcreteCommand, Receiver, Invoker, Client

---

**Q55.**
> 데이터 스트림 절차의 각 단계를 필터로 캡슐화하여 파이프를 통해 전송하는 패턴으로, UNIX의 셸(Shell)이 대표적인 것은?

**정답**: 파이프-필터 패턴(Pipe-Filter Pattern)

**해설**:
- 아키텍처 패턴 (GOF 패턴이 아닌 아키텍처 수준)
- 데이터 처리 흐름: 입력 → [필터1] → [파이프] → [필터2] → [파이프] → 출력
- UNIX 파이프(|): `ls -l | grep .txt | sort` — 각 명령어가 필터
- 각 필터는 독립적으로 동작 → 재사용성·유지보수성 높음
- 컴파일러, 신호 처리 시스템에서 활용

**Q56.**
> 코드의 종류 중, 코드화 대상 항목의 명칭이나 약호와 관계있는 숫자나 문자, 기호를 이용하여 코드를 부여하는 방법으로, **TV−40 : 40인치 TV**와 같이 표현하는 것은?

**정답**: 연상 코드(Mnemonic Code)

**해설**:
- 연상 코드: 코드만 보고도 내용을 유추할 수 있음 (기억하기 쉬움)
- 예: TV-40 (40인치 TV), S-M (스몰 미디엄 사이즈)
- 코드 종류 비교:

| 코드 | 특징 | 예 |
|------|------|-----|
| 순차 코드 | 일련번호 부여 | 001, 002, 003 |
| 블록 코드 | 대분류별 블록 | 1000-1999: 식품 |
| 10진 코드 | 0~9 사용, 소수점 확장 | 도서관 십진 분류법 |
| **연상 코드** | 명칭 관련 문자·숫자 | TV-40, SW-32 |
| 표의 숫자 코드 | 규격·특성을 코드로 | 냉장고-550 (550리터) |

**Q57.**
> 컴퓨터 시스템의 자원들을 효율적으로 관리하며, 사용자가 컴퓨터를 편리하고 효과적으로 사용할 수 있도록 환경을 제공하는 여러 프로그램의 모임으로, 프로세서·기억장치·입출력장치·파일 및 정보 등의 자원을 관리하는 것은?

**정답**: 운영체제(OS; Operating System)

**해설**:
- 운영체제: 하드웨어와 사용자 사이의 **중재자(인터페이스)**
- 주요 기능: 프로세스 관리, 메모리 관리, 파일 관리, 입출력 관리, 보안 관리
- 종류: Windows, Linux, macOS, Android, iOS, UNIX 등
- 목표: 사용자 편의성 + 자원 효율성 극대화

**Q58.**
> 1960년대 AT&T 벨 연구소, MIT, General Electric이 공동 개발한 운영체제로, 시분할 시스템(Time Sharing System)을 위해 설계되었으며, **트리(Tree) 구조의 파일 시스템**을 갖는 것은?

**정답**: UNIX

**해설**:
- 1969년 AT&T 벨 연구소에서 켄 톰슨(Ken Thompson), 데니스 리치(Dennis Ritchie)가 개발
- 특징: 멀티태스킹, 다중 사용자, 트리 구조 파일 시스템, 이식성(C언어로 작성)
- UNIX 구조: 하드웨어 → 커널(Kernel) → 쉘(Shell) → 유틸리티 → 사용자
- Linux는 UNIX를 모방한 오픈소스 OS

**Q59.**
> UNIX에서 가장 핵심적인 부분으로 하드웨어를 보호하고, 프로그램과 하드웨어 간의 인터페이스 역할을 담당하는 것은?

**정답**: 커널(Kernel)

**해설**:
- 커널: UNIX의 핵심 부분, 메모리에 상주
- 기능: 프로세스 관리, 메모리 관리, 파일 시스템 관리, 입출력 제어
- 쉘(Shell): 사용자 명령을 커널에 전달하는 인터페이스 (bash, zsh 등)
- 구조: 사용자 → 쉘 → 커널 → 하드웨어

---

**Q60.**
> 가상기억장치 구현 기법 중, 프로그램을 **동일한 크기**의 블록으로 나눈 후 나뉜 프로그램을 주기억장치의 영역에 적재시켜 실행하는 기법으로, 프로그램을 나누는 단위를 페이지라 하고 주기억장치 단위를 페이지 프레임이라 하는 것은?

**정답**: 페이징(Paging) 기법

**해설**:
- 페이징: 프로그램을 **동일한 크기**의 페이지로 분할, 주기억장치를 페이지 프레임으로 분할
- 내부 단편화 발생 (마지막 페이지가 프레임보다 작을 때)
- 외부 단편화 없음 (동일 크기로 나누므로)
- 세그멘테이션 vs 페이징:

| 기법 | 분할 크기 | 단편화 |
|------|-----------|--------|
| **페이징** | 동일한 크기 (페이지) | 내부 단편화 |
| **세그멘테이션** | 가변 크기 (세그먼트) | 외부 단편화 |

---

**Q61.**
> 페이지 교체 알고리즘 중, 각 페이지가 주기억장치에 적재될 때마다 그때의 시간을 기억시켜 **가장 먼저 들어와서 가장 오래 있었던 페이지**를 교체하는 기법은?

**정답**: FIFO(First In First Out)

**해설**:
- 가장 먼저 들어온 페이지를 가장 먼저 교체
- 구현 단순, 큐(Queue) 자료구조 사용
- **Belady's Anomaly** 발생 가능: 프레임 수를 늘렸는데 페이지 부재율이 오히려 증가하는 역설 현상 (FIFO에서만 발생)

---

**Q62.**
> 페이지 교체 알고리즘 중, **최근에 가장 오랫동안 사용하지 않은 페이지**를 교체하는 기법은?

**정답**: LRU(Least Recently Used)

**해설**:
- LRU: 가장 오래 사용되지 않은(최근에 참조되지 않은) 페이지 교체
- 가장 많이 사용되는 기법, 지역성(Locality) 원리에 기반
- Belady's Anomaly 발생 없음
- 구현: 참조 시간 기록 또는 카운터 사용 → 오버헤드 있음

---

**Q63.**
> 페이지 교체 알고리즘 중, **사용 빈도가 가장 적은 페이지**를 교체하는 기법은?

**정답**: LFU(Least Frequently Used)

**해설**:
- LFU: 참조 횟수(빈도)가 가장 적은 페이지 교체
- 활발히 사용되는 페이지는 참조 횟수가 많아 교체되지 않음
- 단점: 초기에 많이 사용했지만 현재는 안 쓰는 페이지가 남아있을 수 있음

| 알고리즘 | 교체 기준 |
|---------|----------|
| FIFO | 가장 먼저 들어온 것 |
| LRU | 가장 오래 사용 안 한 것 |
| LFU | 사용 빈도 가장 적은 것 |
| NUR | 최근 미참조 (참조비트+변형비트) |
| OPT | 앞으로 가장 오래 안 쓸 것 (이상적, 실현 불가) |

**Q64.**
> 프로세스의 처리 시간보다 페이지 교체에 소요되는 시간이 더 많아지는 현상으로, 다중 프로그래밍 시스템이나 가상기억장치를 사용하는 시스템에서 나타나는 것은?

**정답**: 스래싱(Thrashing)

**해설**:
- 스래싱: 프로세스가 너무 잦은 페이지 부재(Page Fault)를 일으켜 실제 처리보다 페이지 교체에 시간 대부분 소요
- 원인: 다중 프로그래밍 정도가 너무 높을 때
- 예방: **워킹 셋(Working Set)** 활용 → 자주 참조되는 페이지를 주기억장치에 유지
- CPU 이용률 그래프에서 특정 지점 이후 급격히 감소하는 현상

**Q65.**
> 프로세스가 실행되는 동안 주기억장치를 참조할 때 일부 페이지만 집중적으로 참조하는 성질이 있다는 이론으로, 시간 구역성과 공간 구역성으로 구분되는 것은?

**정답**: Locality(지역성)

**해설**:
- 지역성(국부성): 프로세스가 실행될 때 **일부 페이지만 집중적으로** 참조하는 현상
- 두 가지 종류:

| 종류 | 설명 | 예 |
|------|------|-----|
| **시간 지역성** | 최근에 참조된 데이터가 가까운 미래에 다시 참조될 가능성↑ | 루프 내 변수 반복 참조 |

**Q66.**

**Q67.**

**Q69.**

**Q70.**
> CPU 스케줄링 기법 중, 준비상태 큐에서 기다리고 있는 프로세스들 중에서 **실행 시간이 가장 짧은** 프로세스에게 먼저 CPU를 할당하는 기법으로, 가장 적은 평균 대기 시간을 제공하는 것은?

**정답**: SJF(Shortest Job First, 단기 작업 우선)

**해설**:
- 비선점형: 한번 CPU 할당받으면 작업 완료까지 선점 불가
- 평균 대기 시간 최소 (최적의 비선점 스케줄링)
- 단점: 기아(Starvation) 현상 — 긴 작업은 영원히 기다릴 수 있음
- SJF vs SRT: SJF는 비선점형, SRT(Shortest Remaining Time)는 선점형

| 기법 | 선점 | 기준 |
|------|------|------|
| **SJF** | 비선점 | 전체 실행 시간 |
| **SRT** | 선점 | 남은 실행 시간 |

**Q71.**
> CPU 스케줄링 기법 중, 대기 시간과 서비스(실행) 시간을 이용하는 기법으로, **우선순위 = (대기 시간 + 서비스 시간) / 서비스 시간**으로 계산하는 기법은?

**정답**: HRN(Highest Response-ratio Next)

**해설**:
- HRN: SJF의 기아(Starvation) 문제를 보완하기 위해 대기 시간도 고려
- 우선순위 공식: **(대기 시간 + 서비스 시간) / 서비스 시간**
- 대기 시간이 길어질수록 우선순위↑ → 기아 현상 방지
- 비선점형

예시 계산:
- 프로세스 A: 대기 5, 서비스 3 → 우선순위 = (5+3)/3 = **2.67**
- 프로세스 B: 대기 2, 서비스 1 → 우선순위 = (2+1)/1 = **3.00** → B 먼저

**Q72.**

**Q77.**
> TCP/IP 프로토콜 중, 데이터 전송 전에 연결을 설정하지 않는 **비연결형** 서비스를 제공하는 프로토콜로, 실시간 전송에 유리하고 신뢰성보다 속도가 중요시되는 네트워크에서 사용되는 것은?

**해설**:

- 사용 예: 동영상 스트리밍, DNS, DHCP, VoIP
- TCP vs UDP:

| 항목 | TCP | UDP |
|------|-----|-----|
| 연결 방식 | 연결형 (3-way handshake) | 비연결형 |
| 신뢰성 | 높음 (확인 응답) | 낮음 |
| 속도 | 느림 | 빠름 |
| 용도 | 파일 전송, 이메일 | 스트리밍, DNS |

**Q78.**

**Q79.**

**Q80.**
> IGP 중 하나로, RIP의 단점을 해결하여 새로운 기능을 지원하는 인터넷 프로토콜이며, 최단 경로 탐색에 **다이크스트라(Dijkstra) 알고리즘**을 사용하는 것은?

**해설**:

- 최단 경로 기준: **비용(Cost)** — 대역폭, 지연 등을 종합 계산

- 변경된 링크 정보만 LSA(Link State Advertisement)로 전파 (30초마다 전체 전파하는 RIP보다 효율적)

**Q81.**

**Q82.**
> 한 번의 로그인으로 개인이 가입한 모든 사이트를 이용할 수 있게 해주는 시스템은? (영문 약어)

**해설**:
- SSO: 한 번 인증으로 여러 서비스를 별도 로그인 없이 이용

**해설**:

**Q84.**

| 조건 | 설명 |

> DCL 명령어 중, 변경되었으나 아직 COMMIT되지 않은 모든 내용들을 취소하고 데이터베이스를 이전 상태로 되돌리는 명령어는?

**해설**:
- ROLLBACK: 트랜잭션의 변경 사항을 **취소**하고 이전 상태로 복구
- COMMIT과 대응: COMMIT은 변경사항 영구 저장, ROLLBACK은 취소
- COMMIT 후에는 ROLLBACK 불가
- 자동 ROLLBACK: 오류 발생 시 현재 트랜잭션 자동 취소

**Q136.**
> TCP의 신뢰성 있는 연결을 위한 3-way-handshake 과정을 의도적으로 중단시킴으로써 서버를 대기 상태에 놓이게 하여 정상적인 서비스를 수행하지 못하게 하는 공격 방법은?

**해설**:

- 공격 방법:

### [보기 배치 01] 정규화 단계

> 다음 각 설명에 해당하는 정규화 단계를 **보기**에서 골라 쓰시오.
> 
> 보기: `1NF, 2NF, 3NF, BCNF, 4NF, 5NF`

① 테이블의 모든 속성 값이 원자 값만으로 구성된 정규형이다.

② 1NF를 만족하면서, 기본키가 아닌 모든 속성이 기본키에 대해 완전 함수적 종속을 만족하는 정규형이다.

③ 2NF를 만족하면서, 기본키가 아닌 모든 속성이 기본키에 대해 이행적 함수적 종속을 만족하지 않는 정규형이다.

④ 3NF를 만족하면서, 모든 결정자가 후보키(Candidate Key)인 정규형이다.

⑤ 테이블 R에 다중 값 종속(MVD)이 존재할 경우 R의 모든 속성이 A에 함수적 종속 관계를 만족하는 정규형이다.

⑥ 테이블 R의 모든 조인 종속(JD)이 R의 후보키를 통해서만 성립되는 정규형이다.

**정답**:

| 번호 | 정답 | 핵심 키워드 |
|------|------|------------|
| ① | **1NF** | 원자값(더 이상 분해 불가) |
| ② | **2NF** | 완전 함수적 종속, 부분 종속 제거 |
| ③ | **3NF** | 이행적 함수적 종속 제거 |
| ④ | **BCNF** | 모든 결정자가 후보키 |
| ⑤ | **4NF** | 다중 값 종속(MVD) 제거 |
| ⑥ | **5NF** | 조인 종속(JD) 제거 |

**해설**:
- 정규화 순서: **1NF → 2NF → 3NF → BCNF → 4NF → 5NF** (높을수록 강한 정규화)
- 3NF vs BCNF: 3NF는 결정자가 후보키가 아니어도 되지만, BCNF는 **모든 결정자가 반드시 후보키**여야 함
- 실무에서는 3NF 또는 BCNF까지 정규화하는 것이 일반적

### [보기 배치 02] 트랜잭션의 특성(ACID)

> 다음 각 설명에 해당하는 트랜잭션의 특성을 **보기**에서 골라 쓰시오.
> 
> 보기: `원자성(Atomicity), 일관성(Consistency), 독립성(Isolation), 영속성(Durability)`

① 트랜잭션의 연산은 데이터베이스에 모두 반영(Commit)되거나 전혀 반영되지 않아야(Rollback) 한다.

② 트랜잭션이 그 실행을 성공적으로 완료하면 언제나 일관성 있는 데이터베이스 상태로 변환한다.

③ 둘 이상의 트랜잭션이 동시에 병행 실행되는 경우, 어느 하나의 트랜잭션 실행 중에 다른 트랜잭션의 연산이 끼어들 수 없다.

④ 성공적으로 완료된 트랜잭션의 결과는 시스템이 고장 나더라도 영구적으로 반영되어야 한다.

**정답**:

| 번호 | 정답 | 핵심 구분 포인트 |
|------|------|----------------|
| ① | **원자성(Atomicity)** | All or Nothing, Commit/Rollback |
| ② | **일관성(Consistency)** | 실행 전후 일관성 있는 상태 |
| ③ | **독립성(Isolation)** | 병행 실행 시 다른 트랜잭션 간섭 불가 |
| ④ | **영속성(Durability)** | 고장나도 영구 반영 |

### [보기 배치 03] 접근 통제 유형

> 다음 각 설명에 해당하는 접근 통제 유형을 **보기**에서 골라 쓰시오.
> 
> 보기: `MAC(강제 접근통제), DAC(임의 접근통제), RBAC(역할기반 접근통제)`

① 주체와 객체의 등급을 비교하여 접근 권한을 부여하는 방식이다. 시스템이 접근통제 권한을 지정한다.

② 데이터에 접근하는 사용자의 신원에 따라 접근 권한을 부여하는 방식이다. 데이터 소유자가 접근통제 권한을 지정하고 제어한다.

③ 사용자의 역할에 따라 접근 권한을 부여하는 방식이다. 중앙관리자가 접근통제 권한을 지정한다.

**정답**:

| 번호 | 정답 | 핵심 구분 포인트 |
|------|------|----------------|
| ① | **MAC** (강제 접근통제) | 등급 기반, **시스템**이 권한 지정 |
| ② | **DAC** (임의 접근통제) | 신원 기반, **데이터 소유자**가 권한 지정 |
| ③ | **RBAC** (역할기반 접근통제) | 역할 기반, **중앙관리자**가 권한 지정 |

**해설**:
- MAC: 군사·정부 보안 시스템에서 사용 (기밀 등급)
- DAC: Unix/Linux 파일 시스템 권한 (소유자가 읽기/쓰기 설정)
- RBAC: 기업 환경에서 가장 많이 사용 (관리자 역할, 개발자 역할 등)

### [보기 배치 04] 결합도(Coupling) 종류

> 다음 각 설명에 해당하는 결합도의 종류를 **보기**에서 골라 쓰시오.
> 
> 보기: `내용 결합도, 공통 결합도, 외부 결합도, 제어 결합도, 스탬프 결합도, 자료 결합도`

① 한 모듈이 다른 모듈의 내부 기능 및 그 내부 자료를 직접 참조하거나 수정할 때의 결합도. (결합도 가장 강함)

② 공유되는 공통 데이터 영역을 여러 모듈이 사용할 때의 결합도.

③ 어떤 모듈이 다른 모듈의 논리적인 흐름을 제어하기 위해 제어 신호나 제어 요소를 전달하는 결합도.

④ 모듈 간의 인터페이스로 배열이나 레코드 등의 자료 구조가 전달될 때의 결합도.

⑤ 모듈 간의 인터페이스가 자료 요소로만 구성될 때의 결합도. (결합도 가장 약함)

⑥ 어떤 모듈에서 선언한 데이터(변수)를 외부의 다른 모듈에서 참조할 때의 결합도.

**정답**:

| 번호 | 정답 | 핵심 구분 포인트 |
|------|------|----------------|
| ① | **내용 결합도** | 다른 모듈 내부 직접 참조·수정 (가장 강함) |
| ② | **공통 결합도** | 공유 전역 데이터 영역 사용 |
| ③ | **제어 결합도** | 제어 신호(플래그) 전달 |
| ④ | **스탬프 결합도** | 자료 구조(배열·레코드) 전달 |
| ⑤ | **자료 결합도** | 단순 값만 전달 (가장 약함) |
| ⑥ | **외부 결합도** | 외부 선언 변수 참조 |

**해설**:
- 강도 순서 (강 → 약): **내공외제스자** (내용 > 공통 > 외부 > 제어 > 스탬프 > 자료)
- ③④⑥의 구분이 혼동되기 쉬움:
  - 외부 결합도: **변수**(단일 데이터)를 외부에서 참조
  - 제어 결합도: **플래그/스위치** 같은 제어 신호 전달
  - 스탬프 결합도: **배열·레코드** 같은 자료 구조 전달

### [보기 배치 05] 응집도(Cohesion) 종류

> 다음 각 설명에 해당하는 응집도의 종류를 **보기**에서 골라 쓰시오.
> 
> 보기: `기능적, 순차적, 교환(통신)적, 절차적, 시간적, 논리적, 우연적`

① 모듈 내부의 모든 기능 요소들이 단일 문제와 연관되어 수행되는 경우. (응집도 가장 강함)

② 모듈 내 하나의 활동으로부터 나온 출력 데이터를 그 다음 활동의 입력 데이터로 사용하는 경우.

③ 동일한 입력과 출력을 사용하여 서로 다른 기능을 수행하는 구성 요소들이 모였을 경우.

④ 모듈이 다수의 관련 기능을 가질 때 모듈 안의 구성 요소들이 그 기능을 순차적으로 수행하는 경우.

⑤ 특정 시간에 처리되는 몇 개의 기능을 모아 하나의 모듈로 작성할 경우.

⑥ 유사한 성격을 갖거나 특정 형태로 분류되는 처리 요소들로 하나의 모듈이 형성되는 경우.

⑦ 모듈 내부의 각 구성 요소들이 서로 관련 없는 요소로만 구성된 경우. (응집도 가장 약함)

**정답**:

| 번호 | 정답 | 핵심 구분 포인트 |
|------|------|----------------|
| ① | **기능적** 응집도 | 단일 기능만 수행 (가장 강함) |
| ② | **순차적** 응집도 | 앞 출력 → 다음 입력 (데이터 흐름) |
| ③ | **교환(통신)적** 응집도 | 동일 입출력, 다른 기능 수행 |
| ④ | **절차적** 응집도 | 순서만 있음, 데이터 흐름 없음 |
| ⑤ | **시간적** 응집도 | 특정 시간대 실행 묶음 |
| ⑥ | **논리적** 응집도 | 유사 성격 기능들의 묶음 |
| ⑦ | **우연적** 응집도 | 관련 없는 기능의 우연한 집합 (가장 약함) |

**해설**:
- 강도 순서 (강 → 약): **기순교절시논우** (기능 > 순차 > 교환 > 절차 > 시간 > 논리 > 우연)
- ②④ 혼동 주의:
  - **순차적**: 앞 모듈의 **출력**이 다음 모듈의 **입력**으로 사용 (파이프라인처럼 데이터가 흐름)
  - **절차적**: 관련 기능들이 순서대로 실행되지만, 서로 **데이터를 주고받지 않음** (순서만 있음)

### [보기 배치 07] 객체지향 설계 원칙(SOLID)

> 다음 각 설명에 해당하는 SOLID 원칙을 **보기**에서 골라 쓰시오.
> 
> 보기: `SRP, OCP, LSP, ISP, DIP`

① 객체는 단 하나의 책임만 가져야 한다는 원칙.

② 기존의 코드를 변경하지 않고 기능을 추가할 수 있도록 설계해야 한다는 원칙.

③ 자식 클래스는 최소한 부모 클래스의 기능은 수행할 수 있어야 한다는 원칙.

④ 자신이 사용하지 않는 인터페이스와 의존 관계를 맺거나 영향을 받지 않아야 한다는 원칙.

⑤ 의존 관계 성립 시 추상성이 높은 클래스와 의존 관계를 맺어야 한다는 원칙.

**정답**:

| 번호 | 정답 | 이름 | 의미 |
|------|------|------|------|
| ① | **SRP** | 단일 책임 원칙 | 클래스는 단 하나의 책임만 |
| ② | **OCP** | 개방-폐쇄 원칙 | 확장 Open, 수정 Closed |
| ③ | **LSP** | 리스코프 치환 원칙 | 자식이 부모를 대체 가능 |
| ④ | **ISP** | 인터페이스 분리 원칙 | 불필요한 인터페이스 의존 금지 |
| ⑤ | **DIP** | 의존 역전 원칙 | 추상화에 의존 (구체화 X) |

### [보기 배치 11] 이진 트리 순회

> 다음 이진 트리에 대해 각 순회 방법별 방문 순서를 쓰시오.

```
        A
       / \
      B   C
     / \   \
    D   E   F
```

**정답**:

| 순회 | 방법 | 방문 순서 |
|------|------|-----------|
| ① Preorder (전위) | Root→Left→Right | **A → B → D → E → C → F** |
| ② Inorder (중위) | Left→Root→Right | **D → B → E → A → C → F** |
| ③ Postorder (후위) | Left→Right→Root | **D → E → B → F → C → A** |

**해설**:
- 전위(A부터): A → (B의 서브트리: B→D→E) → (C의 서브트리: C→F)
- 중위(D부터): D → B → E → A → C → F (BST에서는 오름차순 출력)
- 후위(D부터): D → E → B → F → C → A (루트가 마지막)

### [보기 배치 12] OSI 7계층

**정답**:

| 번호 | 정답 | 주요 프로토콜·장비 |

| ① | **물리 계층** | 케이블, 리피터, 허브 |

### [보기 배치 23] 암호화 알고리즘 분류

> 다음 암호화 알고리즘을 개인키(대칭키)와 공개키(비대칭키)로 분류하시오.
> 
> 보기: `DES, AES, RSA, IDEA, Skipjack, SEED, ARIA, ECC`

**정답**:

| 분류 | 알고리즘 | 특징 |
|------|---------|------|
| **개인키(대칭키)** | DES, AES, IDEA, Skipjack, SEED, ARIA | 암호화·복호화 **키 동일**, 빠름 |
| **공개키(비대칭키)** | RSA, ECC | **공개키/개인키 쌍**, 느리지만 키 배송 안전 |

**해설**:
- 대칭키: 빠르지만 **키 배송 문제** (같은 키를 안전하게 전달해야 함)

- 국내 표준 암호화 알고리즘: **SEED, ARIA** (대칭키)
- ECC: 타원 곡선 암호화, RSA보다 짧은 키로 동일한 보안 수준
