**Q01.**
> 요구사항 개발 프로세스의 4단계 중, 고객·사용자로부터 요구사항을 수집하는 첫 번째 단계는?

**정답**: 도출(Elicitation)

**해설**:
- 요구사항 개발 4단계 순서: **도출 → 분석 → 명세 → 확인**
- 암기법: **"도분명확"** (도출-분석-명세-확인)

| 단계 | 영문 | 내용 |
|------|------|------|
| ① 도출 | Elicitation | 인터뷰·설문·워크숍으로 요구사항 수집 |
| ② 분석 | Analysis | 완전성·일관성·명확성 검토, 충돌 해결 |
| ③ 명세 | Specification | SRS(소프트웨어 요구사항 명세서) 작성 |
| ④ 확인 | Validation | 명세서가 실제 요구사항을 올바르게 반영했는지 검토 |

---

**Q02.**
> 요구사항 개발 프로세스의 4단계 중, 수집된 요구사항의 완전성·일관성·명확성 등을 분석하여 충돌을 해결하는 두 번째 단계는?

**정답**: 분석(Analysis)

**해설**:
- 도출로 수집된 요구사항을 정제하는 단계
- 요구사항 간 충돌·중복·모호성을 제거하고 우선순위를 부여

---

**Q03.**
> 요구사항 개발 프로세스의 4단계 중, 분석된 요구사항을 문서로 작성하는 세 번째 단계는?

**정답**: 명세(Specification)

**해설**:
- 분석 결과를 **SRS(Software Requirements Specification, 소프트웨어 요구사항 명세서)**로 문서화
- 기능적·비기능적 요구사항을 명확하고 검증 가능하게 기술

**Q04.**
> 요구사항 개발 프로세스의 4단계 중, 작성된 요구사항 명세서가 요구사항을 제대로 반영했는지 검토하는 네 번째 단계는?

**정답**: 확인(Validation)

**해설**:
- 명세서가 실제 이해관계자의 요구를 올바르게 반영했는지 **리뷰·검토·승인**
- 오류를 조기에 발견해 비용 절감 → 이 단계에서 발견한 오류가 구현 후보다 훨씬 저렴하게 수정됨

**Q05.**
> 소프트웨어 비용 산정 기법 중, 소프트웨어의 기능 수(입력, 출력, 조회, 내부 논리 파일, 외부 인터페이스 파일)를 측정하여 비용을 산정하는 기법은? (영문 약어)

**정답**: FP(Function Point, 기능 점수)

**해설**:
- FP법: 소프트웨어 **기능의 수**를 측정하여 규모와 비용 산정
- 5가지 기능 유형:
  - 입력(EI: External Input)
  - 출력(EO: External Output)
  - 조회(EQ: External inQuiry)
  - 내부 논리 파일(ILF: Internal Logical File)
  - 외부 인터페이스 파일(EIF: External Interface File)
- 비교: **COCOMO** = 소스 코드 라인 수(LOC) 기반 산정

**Q13.**
> SQL에서 두 테이블의 조인 중, 기준 테이블과 조인 테이블의 공통 값을 가진 행만 출력하는 조인 방식은?

**정답**: INNER JOIN (내부 조인)

**해설**:
SQL JOIN 전체 비교:

| JOIN 종류 | 설명 |
|-----------|------|
| INNER JOIN | 양쪽에 공통 값이 있는 행만 반환 |
| LEFT OUTER JOIN | 왼쪽 테이블 전체 + 오른쪽 매칭(없으면 NULL) |
| RIGHT OUTER JOIN | 오른쪽 테이블 전체 + 왼쪽 매칭(없으면 NULL) |
| FULL OUTER JOIN | 양쪽 테이블 전체(매칭 없는 부분 NULL) |
| CROSS JOIN | 두 테이블의 모든 조합(곱집합) |
| SELF JOIN | 자기 자신과 조인 |

**Q14.**
> SQL에서 두 테이블의 조인 중, 기준 테이블의 모든 행을 출력하고 조인 테이블에 매칭되는 행이 없으면 NULL로 채우는 조인 방식은?

**정답**: OUTER JOIN (외부 조인) / LEFT OUTER JOIN

**해설**:
- LEFT OUTER JOIN: **왼쪽** 테이블 기준으로 전체 출력
- RIGHT OUTER JOIN: **오른쪽** 테이블 기준으로 전체 출력
- 매칭되지 않는 컬럼은 **NULL**로 채워짐

**Q15.**
> SQL에서 같은 테이블을 두 번 사용하여 자기 자신과 조인하는 방식은?

**정답**: SELF JOIN (셀프 조인)

**해설**:
- 같은 테이블에 **별칭(alias)**을 두 개 붙여 사용
- 예: 직원 테이블에서 직원과 해당 직원의 상사를 같은 테이블에서 조회

```sql
SELECT A.이름 AS 직원, B.이름 AS 상사
FROM 직원 A, 직원 B
WHERE A.상사번호 = B.직원번호;
```

**Q16.**
> 데이터베이스에서 검색 속도를 높이기 위해 특정 컬럼을 기준으로 별도로 구성한 데이터 구조로, 책의 색인처럼 동작하는 것은?

**정답**: 인덱스(Index)

**해설**:
- 인덱스 없이 검색: **전체 테이블 스캔(Full Table Scan)** → 느림
- 인덱스 있으면: B-트리/해시 등으로 **빠른 검색** 가능
- 단점: 삽입·삭제 시 인덱스도 함께 갱신 → 쓰기 성능 저하
- PRIMARY KEY에는 자동으로 인덱스 생성

---

**Q17.**
> 트리 구조를 이용한 인덱스 구현 방식으로, 데이터가 항상 정렬된 상태를 유지하며 삽입·삭제·검색 모두 O(log n)의 성능을 갖는 자료구조는?

**정답**: B-트리(B-Tree)

**해설**:
- DBMS 인덱스의 대표적 자료구조
- 모든 리프 노드가 같은 레벨 → **균형 트리(Balanced Tree)**
- B+ 트리: B-트리의 확장판, 리프 노드끼리 연결 리스트로 연결 → 범위 검색(BETWEEN, >) 더 빠름
- DBMS에서는 B-트리보다 **B+ 트리**를 주로 사용

**Q18.**
> 데이터베이스 분산 기법 중, 테이블의 행(Row)을 기준으로 데이터를 여러 서버에 나누어 저장하는 방식은?

**정답**: 수평 파티셔닝(Horizontal Partitioning) / 샤딩(Sharding)

**해설**:

| 구분 | 설명 |
|------|------|
| 수평 파티셔닝 (Horizontal) | **행(Row)** 기준 분할. 같은 컬럼 구조 유지 |
| 수직 파티셔닝 (Vertical) | **열(Column)** 기준 분할. 자주 사용하는 컬럼 분리 |
| 샤딩(Sharding) | 수평 파티셔닝을 여러 서버에 분산 저장 |

**Q19.**
> SQL에서 집계 함수와 함께 사용하며, 특정 컬럼을 기준으로 그룹화하는 절은?

**정답**: GROUP BY

**해설**:
```sql
SELECT 부서, COUNT(*) AS 인원수, AVG(급여) AS 평균급여
FROM 직원
GROUP BY 부서;
```
- GROUP BY는 **HAVING**과 함께 자주 출제됨
- WHERE: 그룹화 **전** 조건 / HAVING: 그룹화 **후** 조건

---

**Q20.**
> SQL에서 GROUP BY로 그룹화된 결과에 조건을 적용할 때 사용하는 절은?

**정답**: HAVING

**해설**:
```sql
SELECT 부서, COUNT(*) AS 인원수
FROM 직원
GROUP BY 부서
HAVING COUNT(*) >= 5;   -- 그룹화 후 인원 5명 이상인 부서만
```

| 구분 | WHERE | HAVING |
|------|-------|--------|
| 대상 | 개별 행(Row) | 그룹 |
| 집계함수 사용 | 불가 | 가능 |
| 실행 순서 | GROUP BY 이전 | GROUP BY 이후 |

**Q21.**
> SQL에서 NULL 값을 다른 값으로 대체하는 함수로, `NVL(컬럼, 대체값)` 형태로 사용하는 것은? (Oracle 기준)

**정답**: NVL

**해설**:
- Oracle: `NVL(컬럼, 대체값)`
- SQL Server/MySQL: `ISNULL(컬럼, 대체값)` 또는 `IFNULL(컬럼, 대체값)`
- 표준 SQL: `COALESCE(컬럼, 대체값)` (여러 인자 중 첫 번째 NOT NULL 반환)

```sql
SELECT 이름, NVL(급여, 0) FROM 직원;  -- 급여가 NULL이면 0으로 대체
```

**Q22.**
> E-R 다이어그램에서 두 개체 타입 간의 관계 수를 표현하는 것으로, 1:1, 1:N, N:M 등으로 표시되는 것은?

**정답**: 관계 카디널리티(Cardinality) / 대응 수

**해설**:

| 카디널리티 | 예시 |
|-----------|------|
| 1:1 | 사람 ↔ 주민등록번호 |
| 1:N | 부서 ↔ 직원 (한 부서에 여러 직원) |
| N:M | 학생 ↔ 과목 (여러 학생이 여러 과목 수강) |

- N:M 관계는 실제 구현 시 **중간 테이블(교차 테이블)**로 분리

**Q23.**
> 데이터베이스의 회복 기법 중, 변경된 내용을 즉시 디스크에 기록하고 로그에도 기록하는 방식은?

**정답**: 즉각 갱신 기법(Immediate Update)

**해설**:

| 회복 기법 | 설명 |
|-----------|------|
| 즉각 갱신(Immediate Update) | 변경 즉시 DB에 반영 + 로그 기록. UNDO 필요 |
| 지연 갱신(Deferred Update) | 트랜잭션 완료 후 DB에 반영. UNDO 불필요 |
| 검사점(Checkpoint) | 일정 간격으로 체크포인트 저장. 전체 로그 재생 불필요 |
| 그림자 페이지(Shadow Paging) | 변경 전 원본 페이지 유지 |

**Q24.**
> 데이터베이스 설계 단계 순서를 쓰시오. (요구 분석 → ___ → ___ → ___ → 물리적 설계)

**정답**: 개념적 설계 → 논리적 설계 → 물리적 설계

**해설**:

| 단계 | 내용 | 산출물 |

| 상속(Inheritance) | 부모 클래스의 속성/메서드를 자식이 물려받음 | extends, 코드 재사용 |
| 다형성(Polymorphism) | 같은 인터페이스로 다른 동작 | 오버로딩, 오버라이딩 |

**Q30.**
> 객체지향 프로그래밍의 4대 특성 중, 부모 클래스의 속성과 메서드를 자식 클래스가 물려받는 개념은?

**정답**: 상속(Inheritance)

**해설**:
- Java: `class 자식 extends 부모`
- 장점: 코드 재사용, 계층 구조 표현
- **IS-A 관계**: 강아지 IS-A 동물 (강아지는 동물이다)
- 상속 vs 포함(HAS-A): 자동차 HAS-A 엔진 (자동차는 엔진을 가진다) → 포함은 합성(Composition)으로 구현

**Q31.**
> 객체지향 프로그래밍의 4대 특성 중, 같은 메서드 이름이 객체에 따라 다른 방식으로 동작하는 개념은?

**정답**: 다형성(Polymorphism)

**해설**:
- **오버로딩(Overloading)**: 컴파일 타임 다형성 (같은 이름, 다른 매개변수)
- **오버라이딩(Overriding)**: 런타임 다형성 (부모 메서드를 자식이 재정의)
- 예: `동물.소리내기()` → 개는 "멍멍", 고양이는 "야옹"

**Q32.**
> 같은 이름의 메서드를 매개변수의 수나 타입을 다르게 하여 여러 개 정의하는 것은?

**정답**: 오버로딩(Overloading)

**해설**:

| 구분 | 오버로딩(Overloading) | 오버라이딩(Overriding) |
|------|--------------------|---------------------|
| 발생 위치 | 같은 클래스 내 | 부모-자식 클래스 간 |
| 메서드 이름 | 같음 | 같음 |
| 매개변수 | 다름 (수, 타입, 순서) | 같음 |
| 반환 타입 | 달라도 됨 | 같아야 함 |
| 다형성 종류 | 컴파일 타임 | 런타임 |

```java
// 오버로딩 예시
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
```

**Q33.**
> 자식 클래스가 부모 클래스의 메서드를 재정의하여 사용하는 것은?

**해설**:
```java
class 동물 {
    void 소리() { System.out.println("..."); }

class 개 extends 동물 {
    @Override
    void 소리() { System.out.println("멍멍"); }  // 오버라이딩
}
```

**해설**:
소프트웨어 테스트 7대 원칙:

| 원칙 | 설명 |

| 4. **살충제 패러독스** | 같은 테스트 반복 시 새 결함 발견 못함 |
| 5. 테스팅은 정황 의존 | 상황에 따라 테스트 방법이 달라짐 |
| 6. 오류-부재의 궤변 | 결함 없어도 요구사항 불만족이면 의미 없음 |
| 7. 조기 테스팅 | 개발 초기부터 테스팅 시작 |

**Q48.**
> 테스트에서 소프트웨어가 해야 하는 기능을 제대로 수행하는지 검증(Verification)과, 사용자의 요구사항에 부합하는지 확인(Validation)을 통칭하는 것은?

**정답**: V&V(Verification & Validation)

**해설**:

| 구분 | Verification (검증) | Validation (확인) |
|------|-------------------|-----------------|
| 질문 | "제대로 만들고 있는가?" | "올바른 것을 만들고 있는가?" |
| 기준 | 명세서/설계 기준 | 사용자 요구사항 기준 |
| 방법 | 리뷰, 인스펙션, 워크스루 | 테스트, 사용자 수용 테스트 |

**Q49.**

**정답**: 조건 조합 커버리지(Multiple Condition Coverage)

**해설**:
화이트박스 테스트 커버리지(강도 순):

| 커버리지 | 설명 |
|---------|------|
| 구문(Statement) | 모든 실행 문장을 최소 1회 실행 |
| 결정(Decision/Branch) | 모든 분기(T/F)를 최소 1회 실행 |
| 조건(Condition) | 각 조건식의 T/F를 모두 실행 |
| 조건/결정(Condition/Decision) | 조건+결정 커버리지 동시 만족 |
| **조건 조합(Multiple Condition)** | 모든 조건의 T/F 조합 전부 실행 (가장 강력) |
| 경로(Path) | 모든 실행 경로 테스트 |

**Q50.**

**Q55.**
> SQL에서 두 테이블의 모든 행의 조합(곱집합)을 반환하는 조인으로, WHERE 조건을 사용하지 않는 조인은?

**정답**: CROSS JOIN (교차 조인)

**해설**:
- A 테이블 n행 × B 테이블 m행 = n×m 행 반환
- 조건(ON/WHERE) 없이 모든 조합 생성
- 카테시안 곱(Cartesian Product)이라고도 함

```sql
SELECT * FROM 상품 CROSS JOIN 색상;
-- 상품 5개 × 색상 3개 = 15행 반환
```

**Q56.**
> SQL의 집계 함수 중, 그룹 내 고유한 값의 개수를 세는 함수를 쓰시오. (`SELECT _____(DISTINCT 컬럼명)`)

**정답**: COUNT

**해설**:
```sql
SELECT COUNT(DISTINCT 부서) FROM 직원;   -- 중복 제거 후 부서 개수
SELECT COUNT(*) FROM 직원;               -- 전체 행 수
SELECT COUNT(급여) FROM 직원;           -- NULL 제외한 급여 행 수
```
- `COUNT(*)`: NULL 포함 전체 행 수
- `COUNT(컬럼)`: NULL 제외
- `COUNT(DISTINCT 컬럼)`: 중복 제거 후 개수

**Q57.**
> SQL에서 쿼리 내에 또 다른 쿼리를 포함하는 구조로, 메인 쿼리의 조건절이나 FROM절에 사용되는 것은?

**정답**: 서브쿼리(Subquery) / 부속 질의

**해설**:
```sql
-- WHERE절 서브쿼리
SELECT 이름 FROM 직원
WHERE 급여 > (SELECT AVG(급여) FROM 직원);

-- FROM절 서브쿼리 (인라인 뷰)
SELECT * FROM (SELECT 이름, 급여 FROM 직원 WHERE 부서='개발') AS 개발팀;
```
- 스칼라 서브쿼리: SELECT절에 사용, 단일 값 반환
- 인라인 뷰: FROM절에 사용
- 중첩 서브쿼리: WHERE/HAVING절에 사용

**Q58.**
> SQL에서 저장 프로시저(Stored Procedure)와 달리 반드시 반환값(RETURN)이 있어야 하며, SELECT 문 안에서 바로 호출할 수 있는 절차형 SQL은?

**정답**: 사용자 정의 함수(User-Defined Function)

**해설**:

| 구분 | 저장 프로시저(Procedure) | 사용자 정의 함수(Function) |
|------|------------------------|--------------------------|
| 반환값 | 없어도 됨 (OUT 매개변수) | 반드시 RETURN 필요 |
| 호출 방법 | EXEC/CALL로 호출 | SELECT 문 안에서 호출 가능 |
| DML 사용 | 가능 | 제한적 |
| 용도 | 업무 로직 처리 | 값 계산 및 반환 |

**Q59.**
> SQL에서 `SELECT * FROM 학생 WHERE 이름 LIKE '김%';` 에서 `%`가 의미하는 것은?

**정답**: 글자 수에 상관없이 임의의 문자열 (0개 이상의 모든 문자)

**해설**:
LIKE 와일드카드:

| 와일드카드 | 의미 | 예시 |
|-----------|------|------|
| `%` | 0개 이상의 임의 문자열 | `'김%'` → 김으로 시작하는 모든 값 |
| `_` | 정확히 1개의 임의 문자 | `'김_'` → 김 + 1글자 (김철, 김수 등) |

```sql
WHERE 이름 LIKE '%길동'    -- 길동으로 끝나는
WHERE 이름 LIKE '%길%'     -- 길이 포함된
WHERE 이름 LIKE '김__'     -- 김으로 시작하는 3글자
```

**Q60.**
> SQL에서 SELECT 결과를 특정 컬럼 기준으로 오름차순 정렬할 때 사용하는 절은? (키워드 포함하여 쓰시오)

**정답**: ORDER BY 컬럼명 ASC

**해설**:
```sql
SELECT * FROM 직원 ORDER BY 급여 ASC;    -- 오름차순 (기본값)
SELECT * FROM 직원 ORDER BY 급여 DESC;   -- 내림차순
```

- `DESC`: 내림차순
- SELECT 실행 순서: FROM → WHERE → GROUP BY → HAVING → SELECT → **ORDER BY**

**Q61.**
> 웹 보안 공격 중, 공격자가 악성 스크립트를 웹 페이지에 삽입하여 다른 사용자의 브라우저에서 실행시키는 공격은? (영문 약어)

**정답**: XSS(Cross-Site Scripting)

**해설**:

| 공격 | 설명 | 대상 |
|------|------|------|
| **XSS** | 악성 스크립트를 페이지에 삽입 → 다른 사용자 브라우저에서 실행 | 사용자 |
| **CSRF** | 인증된 사용자를 이용해 서버에 의도치 않은 요청 전송 | 서버 |
| **SQL Injection** | 입력란에 SQL 코드 삽입 → DB 조작 | DB |

- XSS 방어: 입력값 검증(이스케이프 처리), CSP(Content Security Policy)

**Q62.**
> 웹 보안 공격 중, 사용자가 이미 인증된 상태를 악용하여 사용자 모르게 의도하지 않은 요청을 서버에 전송시키는 공격은? (영문 약어)

**정답**: CSRF(Cross-Site Request Forgery)

**해설**:
- 공격 시나리오: 사용자가 은행 사이트 로그인 → 악성 링크 클릭 → 자동으로 이체 요청 전송
- 방어: **CSRF 토큰** 사용, Referer 검증, SameSite 쿠키
- XSS vs CSRF: XSS는 스크립트 실행이 목적, CSRF는 요청 위조가 목적

**Q63.**
> 보안 공격 중, 프로그램이 할당된 메모리 경계를 초과하여 데이터를 쓸 때 발생하는 취약점을 이용한 공격은?

**정답**: 버퍼 오버플로우(Buffer Overflow)

**해설**:
- 버퍼(메모리 공간)에 허용 크기를 초과하는 데이터 입력 시 인접 메모리 덮어씀
- 공격자가 **리턴 주소를 악성 코드 주소로 변경** → 임의 코드 실행 가능
- 방어: 입력 길이 검증, 안전한 함수 사용(`strncpy` 대신 `strcpy` 사용 금지), 스택 가드

**Q65.**

**Q67.**

**해설**:

| 보안 장비 | 역할 |

**Q68.**

**해설**:

| 구분 | IDS | IPS |

**Q70.**
> 공개키 기반 구조(PKI)에서 디지털 인증서를 발급하고 관리하는 기관은? (영문 약어)

**정답**: CA(Certificate Authority, 인증 기관)

**해설**:
PKI(Public Key Infrastructure) 구성요소:

| 구성요소 | 설명 |
|---------|------|

| **인증서(Certificate)** | 공개키와 신원 정보를 CA가 서명한 문서 |
| **CRL(인증서 폐지 목록)** | 유효하지 않은 인증서 목록 |

**Q71.**
> 메시지의 내용을 해시함수로 변환한 후 개인키로 암호화하여 메시지에 첨부하는 방식으로, 인증·무결성·부인방지를 제공하는 것은?

**해설**:

1. 송신자: 원문 → 해시 → **개인키로 암호화** → 서명 첨부

- **인증(Authentication)**: 송신자 신원 확인
- **무결성(Integrity)**: 메시지 변조 여부 확인
- **부인방지(Non-repudiation)**: 송신 사실 부인 불가

**Q75.**
> 공유 자원에 오직 하나의 프로세스만 접근할 수 있도록 보장해야 하는 코드 영역은?

**정답**: 임계 구역(Critical Section)

**해설**:
- 공유 자원(메모리, 파일 등)에 여러 프로세스가 동시 접근 시 **경쟁 조건(Race Condition)** 발생
- 임계 구역 내에는 **하나의 프로세스만 진입** 허용
- 상호 배제(Mutual Exclusion) 구현 방법: 세마포어, 뮤텍스, 모니터

**Q76.**
> 임계 구역에 대한 동기화를 위해 정수 변수를 이용하여 프로세스 접근을 제어하는 방법으로, 다익스트라(Dijkstra)가 제안한 것은?

**정답**: 세마포어(Semaphore)

**해설**:
- 정수 변수 S로 프로세스 접근 제어
- `P(S)` (Wait): S > 0이면 S--, 아니면 대기
- `V(S)` (Signal): S++
- 이진 세마포어(Binary Semaphore): S = 0 or 1 (뮤텍스와 유사)
- 계수 세마포어(Counting Semaphore): S ≥ 0 (여러 자원 관리)

**Q77.**

**정답**: 뮤텍스(Mutex)

**해설**:

| 구분 | 세마포어(Semaphore) | 뮤텍스(Mutex) |
|------|-------------------|-------------|
| 값 범위 | 0 이상 정수 | 0 또는 1 |
| 소유 개념 | 없음 | 있음 (잠근 스레드만 해제) |
| 사용 범위 | 프로세스 간 | 주로 스레드 간 |
| 자원 수 | 여러 개 관리 가능 | 1개만 |

### [보기 배치 27] 보안 공격 유형

> 다음 각 설명에 해당하는 보안 공격 유형을 **보기**에서 골라 쓰시오.

〈보기〉 `XSS, CSRF, SQL 삽입, 스니핑, 스푸핑, 피싱, 파밍, 버퍼 오버플로우, 랜섬웨어, SYN Flooding`

| 번호 | 설명 | **정답** |
|------|------|---------|
| ① | 악성 스크립트를 웹 페이지에 삽입하여 다른 사용자 브라우저에서 실행시키는 공격 | **XSS** |
| ② | 인증된 사용자를 이용해 사용자 모르게 의도하지 않은 요청을 서버에 전송하는 공격 | **CSRF** |
| ③ | 입력값에 SQL 코드를 삽입하여 DB를 조작하는 공격 | **SQL 삽입** |
| ④ | 네트워크 패킷을 도청하는 수동적 공격 | **스니핑** |
| ⑤ | 정상적인 웹 사이트처럼 꾸민 가짜 사이트로 유인하여 개인정보를 탈취하는 공격 | **피싱** |
| ⑥ | DNS를 조작하여 정상 도메인 접속 시 가짜 사이트로 강제 이동시키는 공격 | **파밍** |
| ⑦ | 프로그램이 할당된 메모리 경계를 초과할 때 발생하는 취약점 공격 | **버퍼 오버플로우** |
| ⑧ | 파일을 암호화 후 복호화 키를 조건으로 금전을 요구하는 악성 프로그램 | **랜섬웨어** |
| ⑨ | TCP 3-way-handshake를 악용해 서버 연결 대기 큐를 가득 채우는 DoS 공격 | **SYN Flooding** |
| ⑩ | 자신의 IP·MAC 주소를 위조하여 다른 시스템인 척 통신하는 공격 | **스푸핑** |

**구분 포인트**:
- 피싱 vs 파밍: 피싱=가짜 링크 클릭 유도, 파밍=DNS 조작으로 정상 URL도 피해
- 스니핑 vs 스푸핑: 스니핑=도청(수동), 스푸핑=신분 위조(능동)
- XSS vs CSRF: XSS=스크립트 실행, CSRF=위조 요청 전송
- SYN Flooding: TCP 연결 시 SYN→SYN-ACK→ACK에서 ACK를 보내지 않아 서버 자원 소진

### [보기 배치 28] SQL JOIN 종류

> 다음 각 설명에 해당하는 SQL JOIN의 종류를 **보기**에서 골라 쓰시오.

〈보기〉 `INNER JOIN, LEFT OUTER JOIN, RIGHT OUTER JOIN, FULL OUTER JOIN, CROSS JOIN, SELF JOIN`

| 번호 | 설명 | **정답** |
|------|------|---------|
| ① | 두 테이블에서 공통 값을 가진 행만 반환하는 조인 | **INNER JOIN** |
| ② | 왼쪽 테이블의 모든 행과, 오른쪽 테이블에서 매칭되는 행(없으면 NULL)을 반환 | **LEFT OUTER JOIN** |
| ③ | 양쪽 테이블의 모든 행을 반환하고, 매칭되지 않는 부분은 NULL로 채우는 조인 | **FULL OUTER JOIN** |
| ④ | 두 테이블의 모든 행의 조합(곱집합)을 반환하는 조인 | **CROSS JOIN** |
| ⑤ | 동일한 테이블을 두 번 사용하여 자기 자신과 조인하는 방식 | **SELF JOIN** |

**구분 포인트**:
- INNER JOIN: 교집합만 (양쪽 모두 있는 것)
- LEFT/RIGHT OUTER JOIN: 기준 테이블 전체 + 상대 테이블 매칭(없으면 NULL)
- FULL OUTER JOIN: 합집합 (양쪽 모두 전체)
- CROSS JOIN: 곱집합 (조건 없음)
- SELF JOIN: 같은 테이블 두 번 사용 (별칭 필수)

### [보기 배치 30] Git 주요 명령어

> 다음 각 설명에 해당하는 Git 명령어를 **보기**에서 골라 쓰시오.

〈보기〉 `git clone, git add, git commit, git push, git pull, git branch, git checkout, git merge, git rebase, git stash`

| 번호 | 설명 | **정답** |
|------|------|---------|
| ① | 원격 저장소를 로컬로 복제하는 명령어 | **git clone** |
| ② | 변경된 파일을 스테이징 영역에 추가하는 명령어 | **git add** |
| ③ | 스테이징된 변경사항을 로컬 저장소에 기록하는 명령어 | **git commit** |
| ④ | 로컬 커밋을 원격 저장소에 업로드하는 명령어 | **git push** |
| ⑤ | 원격 저장소의 변경사항을 가져와 현재 브랜치에 병합하는 명령어 | **git pull** |

- `merge` vs `rebase`: merge=병합 커밋, rebase=커밋 재배치

### [보기 배치 31] 디스크 스케줄링 알고리즘

> 다음 각 설명에 해당하는 디스크 스케줄링 알고리즘을 **보기**에서 골라 쓰시오.

〈보기〉 `FCFS, SSTF, SCAN, C-SCAN, LOOK`

| 번호 | 설명 | **정답** |
|------|------|---------|
| ① | 요청이 들어온 순서대로 처리하는 가장 단순한 방식 | **FCFS** |
| ② | 현재 헤드 위치에서 가장 가까운 요청부터 처리하는 방식. 기아 현상 발생 가능 | **SSTF** |
| ③ | 헤드가 한쪽 방향으로 이동하며 요청을 처리하고, 끝에 도달하면 반대 방향으로 이동하는 방식 (엘리베이터 알고리즘) | **SCAN** |
| ④ | SCAN과 유사하지만 한쪽 방향으로만 요청을 처리하고, 끝에 도달하면 처음으로 돌아오는 방식 | **C-SCAN** |
| ⑤ | SCAN과 유사하지만 실제 요청이 있는 범위까지만 이동하는 방식 | **LOOK** |

**구분 포인트**:
- FCFS: 가장 단순, 비효율적
- SSTF: 가장 짧은 탐색 시간 우선, 기아 현상
- SCAN: 엘리베이터, 양방향
- C-SCAN (Circular SCAN): 한 방향만, 끝→처음 복귀
- LOOK: SCAN의 개선, 실제 요청 범위만 이동 (디스크 끝까지 안 감)

### [보기 배치 32] HTTP 상태 코드

> 다음 각 설명에 해당하는 HTTP 상태 코드를 **보기**에서 골라 쓰시오.

〈보기〉 `200, 201, 301, 400, 401, 403, 404, 500, 503`

| 번호 | 설명 | **정답** |
|------|------|---------|
| ① | 요청이 성공적으로 처리됨 (OK) | **200** |
| ② | 요청이 성공하여 새 리소스가 생성됨 (Created) | **201** |
| ③ | 리소스가 영구적으로 이동됨 (Moved Permanently) | **301** |
| ④ | 잘못된 요청 문법이나 유효하지 않은 요청 (Bad Request) | **400** |
| ⑤ | 인증 필요 — 로그인하지 않은 경우 (Unauthorized) | **401** |
| ⑥ | 인증은 됐지만 접근 권한 없음 (Forbidden) | **403** |
| ⑦ | 요청한 리소스를 찾을 수 없음 (Not Found) | **404** |
| ⑧ | 서버 내부 오류 (Internal Server Error) | **500** |

**구분 포인트**:
- 2xx: 성공 / 3xx: 리다이렉션 / 4xx: 클라이언트 오류 / 5xx: 서버 오류
- **401 vs 403**: 401=로그인 안 함(인증 없음), 403=로그인했지만 권한 없음(인가 거부)
- **200 vs 201**: 200=조회/수정 성공, 201=생성 성공(POST)
- **301 vs 302**: 301=영구 이동, 302=임시 이동

### [보기 배치 33] 소프트웨어 개발 방법론

> 다음 각 설명에 해당하는 소프트웨어 개발 방법론을 **보기**에서 골라 쓰시오.

〈보기〉 `폭포수(Waterfall), 나선형(Spiral), 프로토타입(Prototype), 애자일(Agile), 스크럼(Scrum), 칸반(Kanban)`

| 번호 | 설명 | **정답** |
|------|------|---------|
| ① | 요구분석→설계→구현→테스트→유지보수 단계를 순차적으로 진행하는 전통적 방법론 | **폭포수(Waterfall)** |
| ② | 계획→위험분석→개발·검증→고객평가의 4단계를 반복하며 위험 최소화에 집중하는 방법론 | **나선형(Spiral)** |
| ③ | 고객에게 시제품을 먼저 제공하고, 피드백을 받아 요구사항을 구체화하는 방법론 | **프로토타입(Prototype)** |
| ④ | 스프린트(Sprint) 단위로 개발을 반복하며, 스크럼 마스터·제품 소유자·개발팀으로 구성되는 애자일 프레임워크 | **스크럼(Scrum)** |
| ⑤ | 칸반 보드로 작업 흐름을 시각화하고 WIP 제한으로 효율성을 높이는 방법론 | **칸반(Kanban)** |

**구분 포인트**:
- 폭포수: 순차적, 단계 역행 불가, 가장 전통적
- 나선형: "위험 분석"이 핵심 키워드, 4단계 반복
- 프로토타입: "시제품", "피드백"이 핵심 키워드
- 스크럼: "스프린트", "스크럼 마스터", "백로그" 키워드
- 칸반: "칸반 보드", "WIP 제한" 키워드
- 스크럼과 칸반 모두 애자일에 속하는 프레임워크

### [보기 배치 34] 테스트 종류 분류

> 다음 각 설명에 해당하는 테스트 종류를 **보기**에서 골라 쓰시오.

〈보기〉 `화이트박스 테스트, 블랙박스 테스트, 단위 테스트, 통합 테스트, 시스템 테스트, 회귀 테스트, 성능 테스트, 부하 테스트, 스트레스 테스트`

| 번호 | 설명 | **정답** |
|------|------|---------|
| ① | 소스 코드의 내부 구조를 보고 테스트. 경로·분기를 기준으로 테스트 케이스 설계 | **화이트박스 테스트** |
| ② | 내부 구조를 모르고 입출력만으로 테스트. 동치 분할, 경계값 분석 등 사용 | **블랙박스 테스트** |
| ③ | 코딩 직후 모듈(함수·클래스) 단위로 수행하는 가장 작은 단위 테스트 | **단위 테스트** |
| ④ | 변경·수정 후 기존 기능이 여전히 동작하는지 확인하는 재테스트 | **회귀 테스트** |
| ⑤ | 시스템이 감당할 수 있는 최대 부하를 초과하는 상황에서의 동작을 확인하는 테스트 | **스트레스 테스트** |

**구분 포인트**:
- 화이트박스: 내부 코드 **보임** (구조 기반), 개발자 수행
- 블랙박스: 내부 코드 **안 보임** (명세 기반), QA 수행
- 단위→통합→시스템→인수: 테스트 범위가 점차 확대
- 회귀 테스트: "기존 기능 이상 없는지" 확인 (수정 후 재테스트)
- 부하 vs 스트레스: 부하=최대 예상 범위 내, 스트레스=최대치 초과
