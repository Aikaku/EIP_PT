```c
int main(void) {
    int n[5];
    int i;

    for (i = 0; i < 5; i++) {
        printf("숫자를 입력해주세요 : ");
        scanf("%d", &n[i]);
    }

    for (i = 0; i < 5; i++) {
        printf("%d", (          ));
    }

}
```

> 입력: 5 4 3 2 1

### 풀이

**입력 후 배열 상태**

```
인덱스:  [0]  [1]  [2]  [3]  [4]
n[]  :    5    4    3    2    1
```

**출력 결과를 보면 43215 → 한 칸씩 뒤에서 출력**

i=0일 때 n[1]=4, i=1일 때 n[2]=3 ... i=4일 때 n[0]=5

→ 인덱스 패턴: `1, 2, 3, 4, 0` = `(i + 1) % 5`

**`%` 연산자 (나머지) 역할**

| i | i+1 | (i+1) % 5 | n[(i+1)%5] | 출력 |
|---|-----|-----------|-----------|------|
| 0 |  1  |     1     |  n[1] = 4  |  4   |
| 1 |  2  |     2     |  n[2] = 3  |  3   |
| 2 |  3  |     3     |  n[3] = 2  |  2   |
| 3 |  4  |     4     |  n[4] = 1  |  1   |
| 4 |  5  |     0     |  n[0] = 5  |  5   |

i=4일 때 `5 % 5 = 0` 이 되어 n[0]으로 돌아오는 것이 핵심 (**순환 배열**)

## Q03

```c
#include <stdio.h>
#include <stdlib.h>
char n[30];
char *test() {
    printf("입력하세요: ");
    gets(n);
    return n;
}
int main() {
    char *test1;
    char *test2;
    char *test3;

    test1 = test();
    test2 = test();
    test3 = test();

    printf("%s\n", test1);
    printf("%s\n", test2);
    printf("%s",   test3);
}
```

> 입력: 홍길동, 김철수, 박영희 순서로 주어진다.

### 핵심 개념

- `char n[30]`은 **전역 변수** → 프로그램 전체에서 단 하나만 존재
- `test()`는 매번 **같은 전역 버퍼 n**에 입력값을 덮어쓰고 **n의 주소**를 반환
- test1, test2, test3은 모두 **같은 주소(n)**를 가리킴

### 메모리 구조

```
전역 버퍼 n: [ 주소: 0x100 ]
                  ↑
test1 = 0x100 ───┤
test2 = 0x100 ───┤  세 포인터 모두 같은 주소
test3 = 0x100 ───┘
```

### 단계별 풀이

```
test1 = test()  →  gets(n): n = "홍길동",  test1 = &n (0x100)
test2 = test()  →  gets(n): n = "김철수",  test2 = &n (0x100)  ← n 덮어씌워짐
test3 = test()  →  gets(n): n = "박영희",  test3 = &n (0x100)  ← n 덮어씌워짐
```

세 번의 `gets(n)` 이후 n에는 마지막 입력인 **"박영희"** 만 남음  
test1, test2, test3 모두 같은 n을 가리키므로 셋 다 **"박영희"** 출력

## Q05

```c
#include <stdio.h>
void main() {
    int n[3] = {73, 95, 82};
    int sum = 0;

    for (int i = 0; i < 3; i++) {
        sum += n[i];
    }

    switch (sum / 30) {
        case 10:
        case 9:  printf("A");
        case 8:  printf("B");
        case 7:
        case 6:  printf("C");
        default: printf("D");
    }
}
```

### 핵심 개념

| 개념 | 설명 |
|------|------|
| `switch` fall-through | `break`가 없으면 매칭된 case 이후 **모든 case를 연속 실행** |
| 정수 나눗셈 | `250 / 30` = **8** (소수점 버림) |

### 단계별 풀이

**① sum 계산**

```
sum = 73 + 95 + 82 = 250
sum / 30 = 250 / 30 = 8  (정수 나눗셈)
```

**② switch(8) 실행**

```
case 10: → 불일치, 건너뜀
case 9:  → 불일치, 건너뜀
case 8:  → 일치! printf("B") 실행
          break 없음 → fall-through ↓
case 7:  → printf 없음, fall-through ↓
case 6:  → printf("C") 실행
          break 없음 → fall-through ↓
default: → printf("D") 실행
```

**fall-through 흐름**

```
case 8  →  "B" 출력
            ↓ (break 없음)
case 7  →  출력 없음
            ↓ (break 없음)
case 6  →  "C" 출력
            ↓ (break 없음)
default →  "D" 출력
```

### 정답

## Q06

프로그램 내에 있는 결정포인트 내의 모든 각 개별 조건식에 대한 모든 가능한 결과(참/거짓)에 대해 적어도 한번 수행한다.  
소프트웨어 테스트 수행시 소스코드를 어느 수준까지 수행하였는가를 나타내는 기준을 나타낸다.  
실제 업무에서는 다양한 툴을 사용하여 테스팅 수행한다.  
True/False에 충분한 영향을 줄 수 없는 경우가 발생 가능한 한계점을 지닌다.  

> 보기: ㄱ. 구문 커버리지  ㄴ. 경로 커버리지  ㄷ. 조건/결정 커버리지  ㄹ. 변형 조건/결정 커버리지  ㅂ. 다중 조건 커버리지  ㅅ. 결정 커버리지  ㅇ. 조건 커버리지

### 핵심 개념

**테스트 커버리지**: 소스코드의 어느 수준까지 테스트가 수행되었는지를 나타내는 기준

### 단계별 풀이

**① 첫 번째 단서 분석**

> "결정포인트 내의 모든 각 **개별 조건식**에 대한 모든 가능한 결과(참/거짓)에 대해 적어도 한번 수행"

→ **개별 조건식** 하나하나가 T/F를 각각 최소 1번씩 → 조건 커버리지 특징

**② 네 번째 단서가 결정적**

> "True/False에 **충분한 영향을 줄 수 없는** 경우가 발생 가능한 한계점"

→ 조건 커버리지의 대표적 한계: 개별 조건이 T/F를 모두 취해도 **전체 결정(Decision) 결과가 T 또는 F만 나올 수 있음**

```
예) A AND B에서 (A=T, B=F), (A=F, B=T) 테스트 시
  → A도 T/F, B도 T/F → 조건 커버리지 충족
  → 하지만 결과는 둘 다 False → 결정이 True인 경우를 테스트 못 함
```

### 각 보기 설명

| 기호 | 이름 | 설명 | 특징/한계 |
|------|------|------|-----------|
| ㄱ | 구문 커버리지 | 모든 구문(statement)이 최소 1번 실행 | 가장 기본적, 조건 T/F 미보장 |
| ㄴ | 경로 커버리지 | 모든 가능한 경로(path)를 최소 1번 실행 | 가장 강력하지만 경우의 수 폭발적 증가 |
| ㄷ | 조건/결정 커버리지 | 결정 커버리지 + 조건 커버리지 동시 충족 | 개별 조건 T/F + 전체 결정 T/F 모두 보장 |
| ㄹ | 변형 조건/결정 커버리지 (MC/DC) | 각 개별 조건이 전체 결정 결과에 **독립적으로** 영향을 줌을 검증 | 항공·의료 등 고신뢰성 시스템 기준 (DO-178B/C) |
| ㅂ | 다중 조건 커버리지 | 결정포인트 내 조건의 **모든 조합(T/F)** 테스트 | n개 조건 → 2ⁿ가지 필요. 가장 완전하나 비용 큼 |
| ㅅ | 결정 커버리지 | 모든 결정포인트에서 **전체 조건식**이 T/F를 각각 최소 1번 | Branch Coverage라고도 함 |
| **ㅇ** | **조건 커버리지** | 결정포인트 내 **각 개별 조건식**이 T/F를 각각 최소 1번 | **한계: 전체 결정(Decision) 결과에 영향 못 줄 수도 있음** |

### 커버리지 강도 (약 → 강)

```
구문 → 결정(Branch) → 조건 → 조건/결정 → 변형 조건/결정(MC/DC) → 다중 조건 → 경로
```

### 정답

**ㅇ. 조건 커버리지**

## Q08

소프트웨어에서 워터마크 삭제 등과 같이 소프트웨어가 불법으로 변경(unauthorized modifications)되었을 경우, 그 소프트웨어가 정상 수행되지 않게 하는 기법이다.  
소프트웨어 변조 공격을 방어하기 위해 프로그램에 변조검증코드(tamper-proofing code)를 삽입하는 것도 한 방법으로, 변조검증코드의 용도는 첫째 프로그램이 변경되었는지를 탐지하는 것이고, 둘째는 변조가 탐지되었다면 프로그램이 실행되지 않게 한다.  
소프트웨어의 위변조 방지 역공학 기술의 일종으로 디지털 콘텐츠의 관련 산업이나 전자상거래 또는 보호해야 할 소프트웨어가 있는 다양한 산업 분야에 적용된다.

### 풀이

**키워드 분석**

| 키워드 | 의미 |
|--------|------|
| 불법 변경 시 정상 수행 불가 | 변조된 소프트웨어 실행 자체를 막음 |
| 변조검증코드(tamper-proofing code) 삽입 | 코드 내부에 무결성 검증 로직 내장 |
| 탐지 + 실행 방지 | 2단계 방어: ① 변조 탐지 → ② 실행 차단 |
| 역공학 기술의 일종 | 소프트웨어 보호 기술 범주 |

**소프트웨어 보호 기술 비교**

| 기술 | 목적 |
|------|------|
| **탬퍼 프루핑 (Tamper Proofing)** | 변조 탐지 → 비정상 동작 또는 실행 차단 |
| 코드 난독화 (Obfuscation) | 역분석을 어렵게 코드 변환 (실행은 정상) |
| 워터마킹 (Watermarking) | 소프트웨어에 저작권 정보를 숨김 삽입 |
| 핑거프린팅 (Fingerprinting) | 사용자별 고유 정보를 삽입해 불법 배포자 추적 |

> 워터마크 **삭제**를 탐지하고 실행을 **막는** 것 → 단순 삽입(워터마킹)이 아닌 **탬퍼 프루핑**

### 정답

**탬퍼 프루핑 (Tamper Proofing)**

## Q09

```c
#include <stdio.h>
#define MAX_SIZE 10

int isWhat[MAX_SIZE];
int point = -1;

int isEmpty() { if (point == -1) return 1; return 0; }
int isFull()  { if (point == 10) return 1; return 0; }

void into(int num) {
    if (point >= 10) printf("Full");
    else isWhat[++point] = num;   // 선증가 후 저장
}

int take() {
    if (isEmpty() == 1) printf("Empty");
    else return isWhat[point--];  // 현재값 반환 후 감소
    return 0;
}

int main() {
    int e;
    into(5); into(2);

    while (!isEmpty()) {
        printf("%d", take());
        into(4); into(1); printf("%d", take());
        into(3); printf("%d", take()); printf("%d", take());
        into(6); printf("%d", take()); printf("%d", take());
    }
    return 0;
}
```

### 핵심 개념

| 함수 | 동작 | 연산자 |
|------|------|--------|
| `into(num)` | push (삽입) | `isWhat[++point]` — 먼저 point 증가, 그 위치에 저장 |
| `take()` | pop (제거) | `isWhat[point--]` — 현재 위치 반환 후 point 감소 |

**스택**: LIFO (Last In First Out) — 마지막에 넣은 것이 먼저 나옴

### 단계별 풀이

**초기 상태**

```
into(5): isWhat[0]=5, point=0
into(2): isWhat[1]=2, point=1

스택: [ 5 | 2 ]  ← top(point=1)
```

**while문 진입** — isEmpty()? point=1 ≠ -1 → 0 → !0=1 → 진입

| 단계 | 동작 | 스택 상태 | 출력 |
|------|------|-----------|------|
| take() | isWhat[1]=2 꺼냄, point=0 | [5] | **2** |
| into(4) | isWhat[1]=4, point=1 | [5,4] | |
| into(1) | isWhat[2]=1, point=2 | [5,4,1] | |
| take() | isWhat[2]=1 꺼냄, point=1 | [5,4] | **1** |
| into(3) | isWhat[2]=3, point=2 | [5,4,3] | |
| take() | isWhat[2]=3 꺼냄, point=1 | [5,4] | **3** |
| take() | isWhat[1]=4 꺼냄, point=0 | [5] | **4** |
| into(6) | isWhat[1]=6, point=1 | [5,6] | |
| take() | isWhat[1]=6 꺼냄, point=0 | [5] | **6** |
| take() | isWhat[0]=5 꺼냄, point=-1 | [] | **5** |

**while 조건 재확인** — isEmpty()? point=-1 → 1 → !1=0 → 종료


## Q11

**(1)** 생성자가 여러 차례 호출되더라도 실제로 생성되는 객체는 하나이고 최초 생성 이후에 호출된 생성자는 최초의 생성자가 생성한 객체를 리턴한다. 주로 DBCP(DataBase Connection Pool)와 같은 상황에서 많이 사용한다.

**(2)** 호스트 객체의 내부 상태에 접근할 수 있는 방법을 제공하여 호스트 객체에 연산을 추가할 수 있도록 한다. 합성 구조의 원소들과 상호 작용하는 데 사용되며, 기존 코드를 변경하지 않고 새로운 기능을 추가하는 방법이다.

### 풀이

**키워드 분석**

| 번호 | 핵심 키워드 | 패턴 |
|------|-------------|------|
| (1) | "객체는 하나", "최초의 생성자가 생성한 객체를 리턴", DBCP | **Singleton (싱글톤)** |
| (2) | "호스트 객체에 연산 추가", "합성 구조", "기존 코드 변경 없이 새 기능" | **Visitor (방문자)** |

### Singleton 패턴

- **분류**: 생성(Creational) 패턴
- **목적**: 클래스의 인스턴스가 오직 **하나만** 생성되도록 보장
- **동작**: 최초 1회만 객체 생성 → 이후 호출 시 동일 객체 반환

```java
// 핵심 구조
class Singleton {
    private static Singleton instance;
    private Singleton() {}  // 외부 생성 차단

    public static Singleton getInstance() {
        if (instance == null)
            instance = new Singleton();  // 최초 1회만
        return instance;  // 이후에는 기존 객체 반환
    }
}
```

**사용 사례**: DBCP, 로그 관리자, 설정 객체 등 — 전역 공유가 필요한 경우

### Visitor 패턴

- **분류**: 행위(Behavioral) 패턴
- **목적**: 객체 구조를 **변경하지 않고** 새로운 연산을 추가
- **동작**: Visitor 객체가 각 Element를 방문(visit)하여 연산 수행

```
핵심 구조:
Element.accept(Visitor v) → v.visit(this)
```

**사용 사례**: 컴파일러 AST 탐색, 파일 시스템 순회 등 합성(Composite) 구조

### 디자인 패턴 분류 요약

| 패턴 | 분류 | 핵심 목적 |
|------|------|-----------|
| Singleton (싱글톤) | 생성 | 인스턴스 1개 보장 |
| Visitor (방문자) | 행위 | 구조 변경 없이 새 연산 추가 |
| Proxy (프록시) | 구조 | 대리 객체를 통한 접근 제어 |
| Decorator (데코레이터) | 구조 | 동적으로 기능 추가 |
| Adapter (어댑터) | 구조 | 인터페이스 변환 |

### 정답

**(1) 싱글톤 (Singleton)**  
**(2) 방문자 (Visitor)**

| (1) | Bell 연구소 Hamming 고안, 1비트 정정, 선형블록/순회부호 | **hamming** |
| (2) | 부가적 정보(Redundancy) 첨가, 수신측이 에러검출 및 **정정** | **FEC** |
| (3) | 오류 발생 시 송신 측에 **재전송 요구** | **BEC** |
| (4) | 저장장치 이동 또는 전송 시 **유실·손상 여부 점검** 기술 | **parity** |
| (5) | 전송 오류 확인을 위한 **체크값을 결정**하는 방식 | **CRC** |

### 개념 정리

**① Hamming Code**
- Bell 연구소 Richard Hamming이 고안
- **1비트 오류 정정**, 2비트 오류 검출 가능
- 데이터 비트 사이에 패리티 비트를 삽입하는 선형 블록 부호

**② FEC (Forward Error Correction, 전진 오류 수정)**
- 송신 측이 **오류 정정 정보(Redundancy)를 함께 전송**
- 수신 측이 재전송 요구 없이 **스스로 오류 검출·정정**
- 예: Hamming Code, 터보 코드, LDPC 등

**③ BEC (Backward Error Correction, 역방향 오류 수정)**
- 오류 검출 시 수신 측이 **송신 측에 재전송 요구**
- ARQ (Automatic Repeat reQuest) 라고도 함
- 오류 검출 방법: **Parity 검사, CRC, 블록합 검사** 등

**④ Parity (패리티)**
- 데이터에 패리티 비트를 추가하여 **유실·손상 여부를 점검**하는 기술
- 저장장치(RAM, RAID) 및 직렬 통신 모두에서 사용
- 홀수 패리티 / 짝수 패리티

**⑤ CRC (Cyclic Redundancy Check, 순환 중복 검사)**
- 다항식 연산으로 **체크값(CRC 값)을 생성**하여 전송
- 수신 측에서 동일 방식으로 체크값을 계산 → 불일치 시 오류 검출
- 네트워크 프레임, 파일 무결성 검증에 사용

**FEC vs BEC 핵심 차이**

| 구분 | FEC | BEC |
|------|-----|-----|
| 오류 정정 주체 | 수신 측 (자체 정정) | 송신 측 (재전송) |
| 재전송 요구 | 없음 | 있음 |
| 부가 정보 | 오류 정정 코드 포함 | 오류 검출 코드만 포함 |

> **EAC, PDS** → 보기의 오답 선택지 (사용 안 함)

**EAC (Error Augmenting Code)**
- 오류를 "증폭"시켜 검출하기 쉽게 만드는 부호화 방식의 개념
- 표준 정보처리기사 커리큘럼에 포함되지 않는 용어로, 수험 문제에서 FEC·BEC와 혼동을 유도하는 **오답 선택지**로 사용됨
- 실제 오류 제어 기술은 Hamming, FEC, BEC(ARQ), CRC, Parity가 핵심

**PDS (Physical Data Sanitization / Parity Data Scheme)**
- 저장 매체의 데이터를 물리적으로 완전 삭제하거나 검증하는 기법을 가리키는 표현으로 쓰이기도 하나, 정보처리기사 시험 범위의 **공식 표준 용어가 아님**
- 이 문제에서는 parity와 혼동을 유도하는 **오답 선택지**로 사용됨

> 시험 전략: 보기에 낯선 용어(EAC, PDS)가 있으면 나머지 확실한 정답들을 먼저 채우고 자연스럽게 제거

### 정답

**(1) hamming  (2) FEC  (3) BEC  (4) parity  (5) CRC**

## Q13

> HDLC 프로토콜 — 프레임 종류 및 동작 모드  
> 보기: ㄱ.연결제어 ㄴ.감독 ㄷ.정보 ㄹ.양방향응답 ㅁ.익명 ㅂ.비번호 ㅅ.릴레이 ㅇ.동기균형 ㅈ.동기응답 ㅊ.비동기균형 ㅋ.비동기응답

### 풀이

**HDLC 프레임 3종류**

| 번호 | 설명 요약 | 정답 |
|------|-----------|------|
| (1) | 첫 비트 0, Seq(송신순서) + Next(응답순서) + P/F 보유 | **ㄷ. 정보** (I-Frame) |
| (2) | 첫 비트 1, 두 번째 비트 0, Type 2비트(4종류), Next만 있고 Seq 없음 | **ㄴ. 감독** (S-Frame) |
| (3) | 첫 두 비트 모두 1, 순서번호 없음, Type(2비트)+Modifier(3비트)=5비트로 종류 구분 | **ㅂ. 비번호** (U-Frame) |

**HDLC 동작 모드**

| 번호 | 설명 요약 | 정답 |
|------|-----------|------|
| (4) | 두 호스트 모두 **혼합국**, 양쪽에서 명령·응답 전송 가능 | **ㅊ. 비동기균형** (ABM) |
| (5) | **불균형** 모드, 주국의 허락 없이 종국에서 전송 가능 | **ㅋ. 비동기응답** (ARM) |

### 프레임 구조 상세

**① 정보 프레임 (I-Frame, Information)**
```
[ 0 | Seq(3비트) | P/F | Next(3비트) ]
  ↑
첫 비트 0 = 정보 프레임 식별자
```
- Seq: 이 프레임의 송신 순서번호
- Next: 다음에 받길 기대하는 수신 순서번호 (ACK 역할)
- P/F: Poll(주→종 전송 허용) / Final(종→주 응답)

**② 감독 프레임 (S-Frame, Supervisory)**
```
[ 1 | 0 | Type(2비트) | P/F | Next(3비트) ]
  ↑   ↑
  10 으로 시작 = 감독 프레임
```
- 데이터 전송 X, **흐름제어·오류제어** 전용
- Seq 없음 (데이터를 보내지 않으므로)
- Type 4종류: RR(수신준비), RNR(수신불가), REJ(거부), SREJ(선택거부)

**③ 비번호 프레임 (U-Frame, Unnumbered)**
```
[ 1 | 1 | Type(2비트) | P/F | Modifier(3비트) ]
  ↑   ↑
  11 로 시작 = 비번호 프레임
```
- 순서번호(Seq, Next) **없음** → 링크 설정·해제·모드 설정에 사용
- Type(2비트) + Modifier(3비트) = **5비트**로 최대 32가지 종류 구분

### 동작 모드 상세

| 모드 | 약어 | 균형/불균형 | 설명 |
|------|------|-------------|------|
| **비동기균형** | ABM | **균형** | 양쪽 모두 **혼합국(Combined)** — 명령·응답 모두 가능 |
| **비동기응답** | ARM | **불균형** | 주-종 구조지만 **종국이 허락 없이** 전송 가능 |
| 정규응답 | NRM | 불균형 | 주-종 구조, 종국은 **반드시 허락받아야** 전송 가능 |

**오답 선택지 설명**

| 보기 | 설명 | 판단 |
|------|------|------|
| ㄱ. 연결제어 | 링크의 연결·해제를 제어하는 개념. HDLC의 U-Frame이 연결제어 기능을 수행하지만, 프레임 종류나 모드의 명칭은 아님 | 오답 — 기능 설명이지 명칭이 아님 |
| ㄹ. 양방향 응답 | ABM(비동기균형)과 혼동 유도. ABM이 양방향 통신을 지원하지만 공식 명칭이 아님 | 오답 — ABM을 설명하는 말이지 용어가 아님 |
| ㅁ. 익명 | HDLC와 무관. 완전한 오답 선택지 | 오답 — 무관한 용어 |
| ㅅ. 릴레이 | 네트워크 계층의 릴레이(중계) 개념. HDLC 프레임/모드와 무관 | 오답 — 무관한 용어 |
| ㅇ. 동기균형 | 표준 HDLC에 존재하지 않는 모드. **비동기균형(ABM)** 과 혼동 유도 | 오답 — HDLC 표준 모드 아님 |
| ㅈ. 동기응답 | NRM(정규응답모드)과 혼동 유도. NRM은 종국이 주국의 허락(poll)을 받아야 응답하는 동기적 특성이 있지만 공식 명칭은 **정규응답(NRM)** | 오답 — NRM의 공식 한국어 명칭이 아님 |

> 핵심: 이 문제에서 유효한 HDLC 동작 모드는 **비동기균형(ABM)**, **비동기응답(ARM)**, **정규응답(NRM)** 세 가지뿐이며, NRM은 보기에 없어 이 문제에서 묻지 않음

### 정답

**(1) ㄷ. 정보  (2) ㄴ. 감독  (3) ㅂ. 비번호  (4) ㅊ. 비동기균형  (5) ㅋ. 비동기응답**

## Q14

```java
public class Main {
    public static void main(String[] args) {
        String str1 = "Programming";             // String Pool
        String str2 = "Programming";             // String Pool (str1과 같은 주소)
        String str3 = new String("Programming"); // Heap 객체 (새로 생성)

        System.out.println(str1 == str2);
        System.out.println(str1 == str3);
        System.out.println(str1.equals(str3));
        System.out.print(str2.equals(str3));
    }
}
```

### 핵심 개념

| 연산 | 비교 기준 | 설명 |
|------|-----------|------|
| `==` | **참조(주소)** | 같은 객체를 가리키는지 비교 |
| `.equals()` | **내용(값)** | 문자열 내용이 같은지 비교 |

**Java String 메모리 구조**

```
String Pool (상수 풀)
┌───────────────────┐
│  "Programming"    │ ← str1, str2 모두 이 주소를 가리킴
└───────────────────┘

Heap (일반 객체 영역)
┌───────────────────┐
│  "Programming"    │ ← str3 = new String(...) → 별도 객체
└───────────────────┘
```

> Java는 문자열 리터럴을 **String Pool**에 저장하고 같은 값이면 **동일 객체 재사용**  
> `new String()`은 Pool과 무관하게 **Heap에 항상 새 객체 생성**

### 단계별 풀이

| 구문 | 비교 | 결과 | 이유 |
|------|------|------|------|
| `str1 == str2` | 참조 비교 | **true** | 둘 다 Pool의 동일 객체 가리킴 |
| `str1 == str3` | 참조 비교 | **false** | Pool 주소 ≠ Heap 주소 |
| `str1.equals(str3)` | 내용 비교 | **true** | "Programming" == "Programming" |
| `str2.equals(str3)` | 내용 비교 | **true** | "Programming" == "Programming" |

### 정답

```
true
false
true
true
```

## Q15

> 보기: DES, RSA, AES, ECC, PKI, ARIA, SEED

### 풀이

**대칭키 vs 비대칭키**

| 구분 | 키 구조 | 특징 |
|------|---------|------|
| **대칭키** | 암호화 = 복호화 (같은 키) | 빠름, 키 전달 문제 발생 |
| **비대칭키** | 공개키(암호화) + 개인키(복호화) | 느림, 키 전달 문제 없음 |

### 보기 각 항목 설명

**[대칭키 암호화]**

| 알고리즘 | 설명 |
|----------|------|
| **DES** | 미국 NIST 1977년 표준화. 56비트 키, 64비트 블록. 키 길이가 짧아 현재 **보안 취약** → 사용 권장 안 함 |
| **AES** | DES의 후속, 2001년 NIST 표준화. 128비트 블록, 128/192/256비트 키. **현재 가장 널리 쓰이는** 대칭키 알고리즘 |
| **ARIA** | 국가정보원·KISA·학계 공동 개발. 128비트 블록, 128/192/256비트 키. 2004년 **대한민국 국가 표준** |
| **SEED** | KISA 개발, 1998년. 128비트 블록, 128비트 키. ARIA 이전의 **국내 표준**, 국내 전자상거래·금융 분야 사용 |

**[비대칭키 암호화]**

| 알고리즘 | 설명 |
|----------|------|
| **RSA** | 1977년 MIT Rivest·Shamir·Adleman 개발. **큰 수의 소인수분해** 어려움을 이용. 키 길이 1024~4096비트. 공개키 암호화 대표 알고리즘 |
| **ECC** | 타원 곡선 암호화. **타원 곡선 이산 로그** 문제의 어려움 이용. RSA보다 **짧은 키로 동등한 보안** 제공 → 모바일·IoT 등 자원 제한 환경에 적합 |

**[분류 외]**

| 항목 | 설명 |
|------|------|
| **PKI** | Public Key Infrastructure (공개키 기반 구조). 암호화 알고리즘이 아니라 **공개키를 신뢰할 수 있게 관리하는 체계**. 구성: CA(인증기관)·RA(등록기관)·디지털 인증서·CRL(인증서 폐지 목록) |

> **PKI 주의**: 암호화 알고리즘이 아니므로 대칭/비대칭 분류에 넣으면 오답

### 정답

- **대칭키**: DES, AES, ARIA, SEED
- **비대칭키**: RSA, ECC
